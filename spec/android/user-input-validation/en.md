# User Input and Validation

Status: draft

## Context

A text field is the one place in an app where the user is asked to be right. Everywhere else they tap something the app already offered; here they produce a value out of their own head, under time pressure, on a keyboard that hides a third of the screen, in a locale whose decimal separator the developer never thought about. The app's answer to that value decides whether the user finishes the task or abandons it — and the two most common answers are both wrong. The first is to say nothing until the user presses Submit, then redisplay the form with a red banner and, in the worst version, an empty field: the user is told they failed, after the fact, and asked to type it again. The second is to say too much too early — an error under an email field after four characters, while the user is still typing the address the app is complaining about. Both come from the same missing decision: *when* is an input judged, and *by whom*.

This spec fixes how the skills of this repository take a value from the user, decide what may be checked on the device and what may not, and tell the user what happened. Its centre is a chain of responsibility — shaping, field check, form check, server decision — in which each stage is allowed to answer only what it can answer honestly, and the server keeps the last word on every domain question. Around that chain sit the mechanics that make it survivable: where input state lives so a rotation or a process death never costs the user a word, how a value is normalised before anyone judges it, how an error reaches a screen-reader user and not only a sighted one, and how a submission that fails leaves the user with their input intact and a next step.

Provenance: desk research (August 2026) over the primary Compose text and input documentation (user input and `TextFieldState`, the validate-input quick guide, autofill, focus traversal, state saving), the UI-layer state-production guidance, the platform security risk pages for SQL injection and clipboard handling, the Credential Manager documentation, the `NumberFormat` reference, plus two standards and research sources: the W3C's WCAG 2.2 success criteria for input assistance, and the usability research on inline validation from Nielsen Norman Group and Baymard. Where a quantitative claim comes from a single research house it is attributed inline rather than stated as fact; for a vendor's own API the vendor's documentation is treated as authoritative rather than as one voice among three, which is this corpus's citation-depth convention (`spec/android/app-architecture/` states it explicitly), and any requirement resting on something less settled than shipped, documented behaviour says so at the requirement itself. One position is recorded as uncertain rather than hardened: the stability tier of the state-based Compose text-field APIs at the time of writing (§B, §Open Questions).

Boundaries: which *component* renders a field and its error — filled versus outlined text fields, the one-variant-per-form rule, label visibility, error text replacing supporting text, selection controls, pickers — is owned by `spec/android/ui-components/` §A. The *wording* of an error message, the empty-state and onboarding patterns, and the research behind minimising typing are owned by `spec/android/app-design-navigation/` §F, which also fixes the baseline timing rule this spec refines: §D below states exactly what it adds and why that is a refinement rather than a contradiction. The rule that the backend decides every domain question — and that client-side input checks are *assistance only* — is owned by `spec/android/app-architecture/` §A, and the state-holder and process-death obligations by its §B; this spec applies both to the input surface rather than restating them. The wire-level error contract, the closed set of failure cases, and the requirement that field-level rejections carry field identity are owned by `spec/android/backend-contract/` §B/§C. Input validation *as a security obligation* — untrusted input from IPC, network, and filesystem, parameterised queries, deep-link and WebView hardening — is owned by `spec/android/security/` §D/§F, and the trust boundary for scanned payloads specifically by `spec/android/barcode-scanning/` §F; §A below routes non-typed input sources into those rules instead of inventing a second set. String externalisation, plurals, and RTL are owned by `spec/android/localization/`. Test lanes, fakes, and accessibility-check wiring stay with `spec/android/test-automation/`. Which channel announces a *result* once the user has left the screen is owned by `spec/android/notifications-alerting/` §C.

Readers: authors of this repository's Android skills that build or audit any surface where a user enters a value, and reviewers judging whether an input surface is honest about who decided what. The operator is a secondary reader only where §G's draft and retry rules affect what they will see in a bug report.

## Goals

- Fix a chain of responsibility for judging input — shaping, field check, form check, server decision — so no stage claims an authority it does not have
- Keep every domain judgement on the backend, and make client-side checks visibly assistive rather than a second, quietly diverging rule set
- Make it impossible for the app to lose what the user typed, through rotation, process death, navigation, or a failed submission
- Fix the timing of an error so it is neither premature nor post-hoc, and make its removal immediate on correction
- Make every error perceivable in text, reachable by a screen reader, and attached to the field that caused it
- Normalise and parse input in a locale-correct way, so a comma in a number is a formatting question and never a rejection
- Route sensitive and assisted input (credentials, autofill, clipboard, scanned values) through the platform paths built for them
- Make the input surface provable in tests, including the adversarial values that ship broken

## Non-Goals

- Component choice and per-component rules for fields, pickers, and selection controls — `spec/android/ui-components/` §A
- Error-message wording, empty states, and form-length research — `spec/android/app-design-navigation/` §F
- The authority rule and the state-holder contract themselves — `spec/android/app-architecture/` §A/§B
- The wire error contract and backend-requirement capture — `spec/android/backend-contract/`
- Untrusted input as a security control set (queries, IPC, WebView, deep links) — `spec/android/security/` §D/§F
- The scanned-payload trust boundary — `spec/android/barcode-scanning/` §F
- Translation, plurals, and RTL layout — `spec/android/localization/`
- Authentication protocol design, session handling, and token storage — `spec/android/security/` §G ("Authentication, session handling, and resilience"), with storage mechanics in its §A; §F here covers only the input surface of signing in

## Requirements

### A. The model — what an input is and who judges it

- **MUST** treat a user-entered value as a *claim*, never as a fact: the device may check whether the claim is well-formed, and only the backend decides whether it is acceptable. This is `spec/android/app-architecture/` §A applied at the keyboard, and its consequence is stated there: a client check is assistance, and the server's answer wins even when the client believed the input was fine. The chain below applies to every value the user produces, whatever component produced it — a typed field, a picker, a toggle, a dictation, a selected file — and not only to text
- **MUST** place every check into exactly one of four stages, and **MUST NOT** let a stage answer a question that belongs to a later one:
  1. **Shaping** — what the field will physically accept as it is typed (character class, maximum length, keyboard type). Runs on every keystroke, produces no error message
  2. **Field check** — whether one value is well-formed on its own: present, parseable, within a length or range the contract states. Produces a field error
  3. **Form check** — whether two or more values are consistent with each other in a way the app can verify without asking (end date not before start date, repeated password matches). Produces a field or form error
  4. **Server decision** — everything else: uniqueness, eligibility, quota, pricing, permission, state transitions, and any rule the business owns. Produces a rejection the client renders (`spec/android/backend-contract/` §B)
- **MUST NOT** implement a rule at stage 2 or 3 that the app cannot derive from the published contract or from the format itself — a length cap the contract states is a field check; "this discount code is invalid" is a server decision no matter how tempting the local shortcut is
- **MUST** keep three representations of an input apart and name which one it is passing: the **raw text** the user typed and can still edit, the **normalised value** (trimmed, case-folded, parsed) that checks run against, and the **transmitted value** the wire contract expects. Rendering the transmitted form back into the field the user is editing is a defect
- **MUST** treat every value that arrives from somewhere other than the user's own keystrokes — a scanned code, a deep link, the clipboard, an autofill provider, a share intent, an IPC extra, a file or image returned by a picker (its name, its declared type, its size, and any metadata the app reads from it) — as untrusted input under `spec/android/security/` §D/§F, and, for scanned payloads specifically, under `spec/android/barcode-scanning/` §F. Arriving pre-filled in a text field grants a value no trust it did not already have — the platform's own worked example of the consequence is a field value reaching a query unparameterised [R9]
- **MUST** report a gap rather than deciding silently when an input's judgement fits none of the four stages (per REQ-6 of `project/requirements/android-engineering-skills.md`)

### B. Input state — where it lives and what it survives

- **MUST** hold input in a state-based text field — a `TextFieldState`, hoisted into the screen's state holder per the bullet below, or created with `rememberTextFieldState()` where the value is genuinely UI-local and no check outside the composable reads it — rather than the value/`onValueChange` pair, because the state-based API removes the asynchronous gap in which a keystroke can be dropped or reordered and carries its own restoration [R1]. Where the project is pinned to a Compose or Material version that does not yet offer the state-based overloads, the value-based form is admissible and the deviation is recorded with the feature (§Open Questions)
- **MUST** keep the input state, and the checks that read it, in the same place as the screen's other state per `spec/android/app-architecture/` §B — the state holder or ViewModel, free of `Context`, which is where the platform's own validation example and its state-production guidance both put them [R2][R8] — except for the UI-local case the bullet above admits, and **MUST NOT** duplicate a field's value into a second holder that can drift from the first
- **MUST** model, per field, at least: the current value, whether the field has been *touched* (the user has entered and left it at least once), the current error if any, and whether a submission is in flight. §D's timing rules are unimplementable without the touched flag, so its absence is a defect rather than a simplification
- **MUST** survive process death with the user's input intact, through `rememberSaveable` for UI-local state or `SavedStateHandle` in the ViewModel [R6]; `spec/android/app-architecture/` §B already requires this for the screen, and this spec makes the input field its strictest case: a restored form shows what the user typed, not an empty field
- **MUST NOT** put anything into saved instance state beyond the small values it is for — the `Bundle` is size-bounded and shared, and an oversized payload fails at runtime [R6]. Attachments, images, and long documents are held in the data layer with only their identifier saved
- **MUST NOT** discard input on any path the user did not choose: a failed submission, a server rejection, a rotation, a returned-to screen, a permission prompt, or an expired session all keep the entered values available for correction. WCAG's redundant-entry criterion states the same obligation from the accessibility side: information previously entered is not asked for again in the same process [R12]
- **SHOULD** treat a long or multi-step form as draft-bearing state that outlives the screen — persisted through the data layer per `spec/android/app-architecture/` §C rather than through the `Bundle` — and **MUST** then tell the user that a draft exists and let them discard it

### C. Shaping the input before anyone judges it

- **MUST** configure the keyboard per field — `KeyboardType` matching the value, `KeyboardCapitalization` matching its semantics, autocorrect disabled for identifiers, codes, and anything the dictionary will corrupt, and an `ImeAction` that matches the field's position (`Next` in a chain, `Done`/`Go` at its end) [R1]. `spec/android/app-design-navigation/` §F already requires correct keyboard types; this spec adds that the IME action is part of that configuration and that pressing it moves focus rather than doing nothing
- **MUST** use `InputTransformation` for hard limits that a user can see the effect of — a maximum length, a digits-only field, a fixed character class — and **MUST NOT** use it to silently drop characters whose rejection the user cannot explain to themselves. A filter the user experiences as "my keyboard is broken" is a field check wearing the wrong stage's clothes [R1]
- **MUST** use `OutputTransformation` for display formatting — grouping separators, phone-number punctuation, masks — so the formatting never enters the stored value, and **MUST NOT** write formatted text back into the state the checks run against [R1]
- **MUST** normalise before checking and before transmitting: trim leading and trailing whitespace, collapse the whitespace a paste introduces, and apply the case folding the contract expects — while leaving the user's raw text on screen untouched until they leave the field
- **MUST** parse numbers, dates, and times through locale-aware parsing (`NumberFormat` and the platform's date/time formatting APIs) rather than `toInt()` / `toDouble()` on user text: the decimal and grouping separators differ by locale, and a value that is correct in the user's locale must not be rejected as malformed [R11]. Locale selection and formatting policy stay with `spec/android/localization/`
- **MUST NOT** ask for a value the app can obtain without asking — a value it already stored, one the platform can fill (§F), or one derivable from a value already entered [R12]
- **SHOULD** state the expected format before the user types it (a hint, an example, a prefix) rather than only after they get it wrong; WCAG requires labels or instructions wherever content requires input [R12], and an error avoided needs no message
- **MUST** keep the field being edited and the form's submit control visible while the keyboard is open: the IME is an inset per `spec/android/app-design-navigation/` §A (`Modifier.imePadding()`/`WindowInsets.ime` on the form container, `Modifier.imeNestedScroll()` on a scrolling form, `android:windowSoftInputMode="adjustResize"` under edge-to-edge) — this spec adds the two form-specific consequences: a field that receives focus programmatically (§D's move-to-first-error, an `ImeAction.Next` chain) is brought into view with `BringIntoViewRequester` when the layout cannot guarantee it, and the last field of a scrolling form is kept above the system bars with a `Spacer(Modifier.windowInsetsBottomHeight(WindowInsets.systemBars))` rather than content padding, which the platform documents as the case where the IME otherwise hides the field [R17][R18]. A submit control the keyboard covers, or a focused field scrolled out of view, is a defect of the input surface, not a cosmetic one

### D. Validation — when a check runs and what it is allowed to conclude

- **MUST** raise a field error no earlier than the moment the user leaves the field, and **MUST NOT** raise one while the user is still typing into it for the first time. This governs the *pre-submission* phase: on submission the whole form is validated per the bullet below, which is what surfaces the error on a required field the user never entered and therefore never left. This is `spec/android/app-design-navigation/` §F's rule ("validation on field exit, never while typing"), and it is not restated here for emphasis: the bullet below refines it in the one direction that rule leaves open, and the refinement is deliberate rather than an oversight
- **MUST** clear a displayed error as soon as the input becomes valid, re-checking on each keystroke *while an error is showing*. §F of `spec/android/app-design-navigation/` forbids raising an error during typing; it does not address removing one, and leaving a stale error on screen after the user has fixed it is what the research reports as the more damaging failure — users kept re-reading an error that no longer applied and could not tell whether their correction had registered [R15]
- **MAY**, where a value has a known fixed length, act on the *completion* of that length before the field is left — advancing focus, enabling the next step, or submitting a one-time code — because there the "still typing" state has a defined end [R15]; it **MUST NOT** turn that early check into a displayed error, which `spec/android/app-design-navigation/` §F forbids without exception. Whether that rule should carry an explicit error-on-completion carve-out is a question for that spec, not a deviation to be taken here (§Open Questions)
- **MUST** validate the whole form on submission regardless of what was checked earlier, and **MUST** move focus to the first field in error so a keyboard or screen-reader user is not left to hunt for it [R7]
- **MUST NOT** use a disabled submit control as the only statement of what is wrong: a control that cannot be pressed and does not say why leaves the user without a next step. Either the control stays enabled and pressing it surfaces the errors, or its disabled state is accompanied by a visible statement of the condition that would enable it
- **MUST** treat an asynchronous check (a uniqueness lookup, a server-side format check) as advisory until submission: it is debounced rather than run per keystroke, it is cancelled when the value changes again, it never blocks typing, and its pending state never blocks submission — the authoritative answer arrives with the server decision (§A stage 4)
- **MUST** derive every field check's parameters — required-ness, length, range, allowed values — from the backend contract where one exists, and **MUST** raise a backend requirement per `spec/android/backend-contract/` §E rather than inventing a limit when the contract does not state one
- **SHOULD** prefer preventing the error to reporting it wherever the platform offers the choice: a picker instead of a typed date, a selection instead of a free-text enumeration, a formatted mask instead of a format lecture — the same progressive-disclosure and minimise-typing rules `spec/android/app-design-navigation/` §F applies to form design

### E. Feedback — how the user learns what happened

- **MUST** identify the field in error and describe the error **in text**, not by colour, border, or icon alone — WCAG 2.2 Success Criterion 3.3.1 (Level A) requires exactly this, and colour-only signalling additionally fails `spec/android/app-design-navigation/` §A's rule against colour as the sole carrier of meaning [R12][R13]
- **MUST** place the message adjacent to the field it concerns, so the user can read it while fixing the input rather than remembering it [R14]; the component that renders it (supporting text replaced by error text, `isError`) is owned by `spec/android/ui-components/` §A, and the wording rules by `spec/android/app-design-navigation/` §F
- **MUST** suggest the correction where the app knows it — a format, an allowed range, the nearest valid value — since WCAG 3.3.3 (Level AA) requires a suggestion whenever one is known and stating it does not compromise security or purpose [R12]
- **MUST** expose the error to accessibility services through `Modifier.semantics { error(...) }` on the field, so a screen reader announces the error with the field rather than leaving it as unattached visual text [R3]
- **MUST** announce a form-level status change — submission failed, submission succeeded, an asynchronous check completed — through a live region (`Modifier.semantics { liveRegion = LiveRegionMode.Polite }`), which is what WCAG's status-message criterion requires programmatically [R3][R12], and **MUST NOT** use `announceForAccessibility()` or `TYPE_ANNOUNCEMENT` events, which are deprecated as of Android 16 [R16]
- **MUST**, for a form long enough that its errors do not fit on one screen, provide an error summary *in addition to* the per-field messages, never instead of them [R14]
- **MUST** give the input surface the accessibility structure a screen-reader user navigates by: form section titles carry `Modifier.semantics { heading() }` so they appear in heading navigation; a custom control that is not a Material component reserves its touch target with `Modifier.minimumInteractiveComponentSize()` (48dp, configurable through `LocalMinimumInteractiveComponentSize`) rather than a hand-set size; a custom toggle, required-marker, or selection state that the default role does not express sets `stateDescription`; and where the visual order differs from the order in which the form should be read — an error summary rendered beside the fields, a two-column form on a large window — the reading order is fixed with `isTraversalGroup` on the container and `traversalIndex` on its children, never left to the default sort [R3][R19][R20]
- **MUST** map a server rejection back to the field that caused it wherever the contract carries field identity, per `spec/android/backend-contract/` §B, and **MUST NOT** render the raw server string as the primary message; a rejection without field identity is a form-level error that still names what to do next
- **MUST** confirm or make reversible any submission that carries a legal, financial, or data-destroying consequence — WCAG 3.3.4 (Level AA) requires the submission to be reversible, checked, or confirmed [R12]; which surface asks (dialog versus undo) follows `spec/android/ui-components/` §A and `spec/android/app-design-navigation/` §F
- **MUST** make success as legible as failure: the app states what changed, and where the user has already left the screen, the channel is chosen per `spec/android/notifications-alerting/` §C rather than by posting a notification reflexively

### F. Sensitive and assisted input

- **MUST** obtain credentials through Credential Manager — passkeys, saved passwords, or federated sign-in — rather than building a bespoke username-and-password surface; it is the platform's recommended API and replaces the legacy sign-in paths [R5]. A hand-rolled credential form is admissible only where the backend supports no mechanism Credential Manager covers, and that gap is recorded as a backend requirement per `spec/android/backend-contract/` §E
- **MUST** mark every autofillable field with its content type — `Modifier.semantics { contentType = ContentType.… }` — so password managers and the platform can fill it; WCAG's input-purpose criterion requires the purpose to be programmatically determinable, and the platform requires the semantic to be present for autofill to work at all [R4][R12]
- **MUST** use the new-credential content types (`ContentType.NewUsername`, `ContentType.NewPassword`) on registration and change-credential forms, and commit deliberately with `AutofillManager.commit()` where the save moment is a button rather than a navigation [R4]
- **MUST** render secret input through `SecureTextField` with an explicit obfuscation mode rather than a plain field with a visual transformation, and **MUST NOT** enable autocorrect, suggestions, or dictionary learning on a secret field [R1]. `SecureTextField` exists only in the state-based form, so where §B's recorded deviation applies — the project's pinned versions do not offer the state-based overloads — the value-based field with a password visual transformation is the admissible fallback under that same recorded deviation, and the autocorrect and suggestion prohibition holds unchanged
- **MUST NOT** block pasting into any credential field, and **MUST NOT** require the user to retype a secret they can neither see nor autofill: WCAG 3.3.8 (Level AA) forbids authentication steps that rest on a cognitive-function test unless an alternative or a mechanism to assist exists, and paste is the mechanism [R12]
- **MUST** flag sensitive values the app itself places on the clipboard with `ClipDescription.EXTRA_IS_SENSITIVE`, so the system does not render them in the clipboard preview [R10]
- **MUST NOT** collect a value the feature does not need, and **MUST NOT** log input content anywhere — `spec/android/security/` §A's log-hygiene rule applies to every field, and a validation failure is logged by field name and reason, never by value

### G. Submission and its outcome

- **MUST** permit exactly one in-flight submission per form: the control is disabled or the intent is ignored while a submission is pending, and the pending state is visible. A double-tap that produces two writes is a defect, and where the write is retried automatically it is idempotent-safe on the wire per `spec/android/app-architecture/` §D and `spec/android/backend-contract/` §C
- **MUST** keep the entered values readable while a submission is in flight, and **MUST** restore full editability on failure without the user re-entering anything (§B)
- **MUST** distinguish, in what the user sees, a rejection of their input from a failure of the transport: a domain rejection names the field or rule and asks for a change; an offline or server fault names retry as the next step and does not imply the user did anything wrong. The closed set of cases and their mapping is owned by `spec/android/backend-contract/` §B
- **MUST NOT** navigate away from a form whose submission has not been confirmed by the backend, unless the write is explicitly a queued or local-first write under `spec/android/app-architecture/` §D — in which case the pending state travels with the data and is visible where the data is shown
- **MUST** guard destructive or irreversible submissions per §E, and **MUST** keep the confirmation about consequence rather than ceremony — `spec/android/app-design-navigation/` §F's undo-over-confirmation rule decides which of the two applies
- **SHOULD** clear a persisted draft (§B) only after the backend has confirmed the write, so a failure at the last step does not also destroy the user's work
- **SHOULD** return the user to a state that shows the result of what they did — the created record, the updated list — rather than to a generic screen that leaves them checking whether it worked

### H. Verification and testing

- **MUST** implement every field and form check as a pure function over the normalised value, testable on the JVM without a device, and **MUST** unit-test each one — this is the level at which `spec/android/test-automation/` §B's ViewModel and edge-case coverage rule becomes concrete for input
- **MUST** cover, for every input surface, at least these values as tests: empty, whitespace-only, at and beyond the maximum length, a value valid in another locale (a comma decimal separator), a pasted value with surrounding whitespace or line breaks, a Unicode value including combining marks or emoji, and — where the field is populated from a non-typed source per §A — the adversarial payload that source can carry
- **MUST** test the timing contract, not only the outcome: no error before first field exit, an error after it, and the error gone on the keystroke that fixes the value
- **MUST** test the restoration path at the level the input actually lives: `StateRestorationTester` for UI-local state held in `rememberSaveable`, and — because that helper recreates only the composition, leaving a ViewModel alive — a direct round-trip test over the `SavedStateHandle` keys wherever §B places the input in the state holder. Asserting only the first proves nothing about the second, and a broken saver or key would pass [R6]
- **MUST** cover the server-rejection path with a fake that produces a field-identified domain rejection from the closed set of `spec/android/backend-contract/` §B, asserting the error lands on the field and the input is preserved
- **SHOULD** assert the accessibility contract in Compose tests — the field carries its error semantics, the status message is a live region — and run the accessibility checks `spec/android/test-automation/` §E wires into the suite
- **SHOULD** assert focus behaviour on submission failure (focus moves to the first field in error), since it is invisible to a sighted mouse-free reviewer and load-bearing for everyone else

## Acceptance Criteria

The criteria below are a deliberate representative rollup of §A–§H, not a 1:1 mapping; every requirement bullet above is normative on its own.

- [ ] Every check in an input surface is assigned to one of the four stages, and no client-side check answers a domain question; a check with no basis in the contract or the format was raised as a backend requirement instead of implemented
- [ ] Raw, normalised, and transmitted representations of each value are distinguishable in the code, and the field the user edits never shows the transmitted form
- [ ] Every value entering a field from a non-typed source is validated as untrusted input under the security rules before anything acts on it
- [ ] Input lives in state-based text fields (or a recorded deviation), in the screen's state holder — or, for a genuinely UI-local value no outside check reads, in `rememberTextFieldState()` — with a per-field touched flag, error, and submission state
- [ ] A simulated process-death restore returns every entered value; no failed submission, rejection, rotation, or permission prompt loses input; nothing oversized is written into saved instance state
- [ ] Every field declares its keyboard type, capitalization, autocorrect setting, and IME action, and the IME action moves focus or submits
- [ ] Input filters are used only for limits the user can perceive; display formatting never enters the stored value
- [ ] Numbers, dates, and times are parsed locale-aware; a comma decimal separator is accepted where the locale uses one
- [ ] Before submission, no field error appears until the user has left the field for the first time — including on a fixed-length field, where acting on completion is permitted but showing an error early is not — while submission validates every field including those never entered; and every displayed error disappears on the keystroke that makes the value valid
- [ ] Submission validates the whole form and moves focus to the first field in error; no disabled control is the sole explanation of what is wrong
- [ ] Asynchronous checks are debounced, cancellable, non-blocking, and never treated as the authoritative answer
- [ ] Every error is stated in text next to its field, carries a correction suggestion where one is known, and is exposed through `Modifier.semantics { error(...) }`; form-level status changes are announced through a live region and never through the deprecated announcement APIs; section titles are headings, custom controls meet the 48dp minimum through `minimumInteractiveComponentSize`, and any non-default reading order is fixed through traversal semantics
- [ ] With the keyboard open, the focused field and the submit control stay visible; a programmatically focused field is brought into view; the activity declares `adjustResize`
- [ ] Server rejections land on the field the contract identifies, with the raw server string never used as the primary message
- [ ] Credentials go through Credential Manager or a recorded gap; autofill content types are set on every fillable field; secret fields use `SecureTextField` — or, under §B's recorded version deviation, a password visual transformation — with autocorrect and suggestions off; pasting into credential fields is never blocked
- [ ] Sensitive values the app copies carry the sensitive-clipboard flag, and no input content appears in any log
- [ ] One submission is in flight at a time, its pending state is visible, input stays intact through failure, and input rejections are visibly distinct from transport failures; irreversible submissions are confirmed or reversible
- [ ] No form asks for a value the app already holds or can obtain without asking; where a field does not state its expected format before the user types, the deviation from §C's SHOULD is a recorded one
- [ ] A form whose errors exceed one screen carries an error summary in addition to its per-field messages
- [ ] A successful submission is as legible as a failed one — the app states what changed — and no screen leaves a form whose submission the backend has not confirmed, unless the write is explicitly queued or local-first with a visible pending state; returning to a state that *shows* the result is §G's SHOULD, and a deviation from it is recorded rather than failed
- [ ] A persisted draft is cleared only after the backend confirms the write, or the deviation from §G's SHOULD is recorded
- [ ] Validation functions are pure and unit-tested; the adversarial value set, the timing contract, the restoration path (at both levels §H names), and the server-rejection path are covered by tests, and the focus behaviour is covered or its deviation from §H's SHOULD recorded

## Open Questions

Each question is marked **parking-lot** — none blocks a skill from running this spec today, because each already has a working default fixed in the requirements above.

- **State-based text-field stability** (parking-lot). The platform documentation presents the state-based text fields as the recommended direction while noting that the Material overloads carried an experimental marker in the version line documented at retrieval time [R1]. §B therefore requires the state-based API with a recorded deviation where the project's pinned versions do not offer it, rather than fixing a version floor this spec cannot verify. Revisit when the overloads are stable in the versions this repository's projects pin.
- **Positive validation feedback** (parking-lot). The research recommends confirming valid fields visually, reporting reduced cognitive load and momentum through long forms [R15]; the platform's own component guidance does not provide a success state for text fields. §D therefore requires only that errors clear, and success confirmation stays optional. Revisit if a component-level success state appears in the design system.
- **Draft persistence scope** (parking-lot). §B requires drafts for long or multi-step forms without defining "long". Whether a field count, a step count, or an expected-completion-time threshold is the right trigger is unresolved; until it is, the judgement stays with the implementing skill and is recorded with the feature.
- **Fixed-length error timing** (parking-lot). `spec/android/app-design-navigation/` §F forbids raising an error while the user types, without exception, while the research reports the fixed-length field as the one case where "still typing" has a defined end and an early error is not premature [R15]. §D therefore permits only acting on completion, never showing an error early. Whether that sibling rule should carry an explicit carve-out for fixed-length fields is a question for it, and until it is answered the stricter reading stands.
- **Shared validation vocabulary** (parking-lot). Every app repeats the same handful of field checks (email shape, required, length, range). Whether this corpus should fix a shared checks module — and where it would live under `spec/android/project-structure/` — is unresolved; until it is, checks are per-feature pure functions per §H.
