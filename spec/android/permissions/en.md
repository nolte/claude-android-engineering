# App Permissions

Status: draft

## Context

A permission is not a line in a manifest — it is a claim an app makes about itself, and almost every app makes that claim too broadly. The failure is structural rather than careless: a developer starts from a capability ("we need the camera"), reaches for the permission whose name matches, and never asks whether the platform offers a path that needs no permission at all. The result is an app that holds a grant it cannot justify, shows a prompt it did not have to show, and gets denied — because a permission the user cannot connect to anything they asked for is the one they refuse. The second failure arrives from the other direction: a library injects a permission into the merged manifest, nobody looks at the merged manifest, and the app ships asking for location it never uses.

This spec fixes how the skills of this repository *determine* which permissions an app genuinely needs, and how those permissions are then *recorded* in the app so the declaration, the runtime request, the degradation path, and the store-facing justification all say the same thing. Its centre is a derivation method — feature to capability to API to permission, with a permission-free alternative rejected on evidence at every step — and a per-permission record that makes the resulting set auditable instead of accidental. The mechanics that follow from that decision (manifest attributes, the request flow, the families whose rules differ, the tooling that proves the actual set) are specified because a correct derivation recorded incorrectly is still a wrong app.

Provenance: desk research (August 2026) over the primary Android permission documentation (the permissions overview, declaring, evaluating, requesting, requesting-special, explaining-access, and best-practice pages), the per-domain permission pages (location, Bluetooth, notifications, media and storage, foreground service types, exact alarms, package visibility, app hibernation), the manifest-element and manifest-merger references, the Android 14, Android 16, and Android 17 behaviour-change and feature pages (including the local-network-permission guide and the contact-picker guide), the health-services permission page, the Wi-Fi permission page, the Live-Update notification guide, the `android.provider.Settings` reference read against AOSP, the `apkanalyzer` tool reference, the `androidx.annotation.RequiresPermission` reference, and the Google Play policy on permissions and APIs that access sensitive information. Nothing here rests on a first-party measurement; one position that the rendered documentation states less sharply than practice demands — the experimental status of the Compose permission wrapper [R27] — is recorded as such rather than turned into a confident requirement (§E, §Open Questions). Two positions an earlier revision left open — the local-network enforcement state and the promoted-notification settings constant — are now settled against primary sources in §F [R31][R32][R33].

Boundaries: permission *minimalism as a security obligation*, the Data Safety declaration, third-party SDK data flows, and the AccessibilityService prohibition are owned by `spec/android/security/` §E, and component-level hardening (`android:exported`, `PendingIntent` immutability, explicit intents) by its §D. Custom permissions are **not** covered there and are therefore normative here: §D below carries the full rule, both as part of an app's declared set and as the access control on its own components. In-context request timing, rationale wording, error-state wording, and the evidence on grant rates belong to `spec/android/app-design-navigation/` §F; this spec states *when* a request is legitimate, not how its copy reads. The camera-permission decision for scanning is settled in `spec/android/barcode-scanning/` §G and the USB/`CAMERA` pair for external microscopes in `spec/android/uvc-microscope/` §C; both are worked examples of §C here and stay authoritative for their surface. ADB mechanics (`pm grant`, `appops set`, `dumpsys`, `install -g`) are owned by `spec/android/adb-workflows/`; this spec references those commands as verification steps rather than redefining them. Test lanes and the emulator-versus-device split stay with `spec/android/test-automation/`. Play-Store *release* — declaration forms filed in the Console, store listings, the Data Safety questionnaire — is out of this repository's scope per `project/requirements/android-engineering-skills.md`; §G specifies only the code-side obligations and the handoff that hands the rest to the operator.

Readers: authors of this repository's Android skills that add, remove, or audit a permission, and reviewers judging whether an app's permission set is derived, declared, requested, and degraded correctly. The operator is a secondary reader: §B's ledger and §G's declaration handoff are written *for* them, so the artifact has to be legible without the spec in hand.

## Goals

- Make the permission set a *derived* result with a written trail — feature to capability to API to permission — instead of an accumulated one
- Force the permission-free alternative to be considered and rejected on evidence before any permission is declared
- Make the declaration conform: correct element, correct scoping attributes, correct feature pairing, no permission the app cannot name a use case for, no permission a library smuggled in
- Fix a single runtime request flow (check, rationale, request, respond, degrade) that never dead-ends the user and never re-prompts into a dialog the system will not show
- Cover the permission families whose rules genuinely differ, so the common cases are not derived from first principles every time
- Make the actual permission set provable from the merged manifest and the installed app, not assumed from the source manifest
- Name the Play-policy obligations that constrain the *code*, and hand the store-side declarations to the operator instead of silently ignoring them

## Non-Goals

- Permission UX copy, prompt timing rationale, and the research behind in-context requests — `spec/android/app-design-navigation/` §F
- The security baseline that permission minimalism serves, and the Data Safety declaration's accuracy — `spec/android/security/` §E
- Component-level access control as an IPC hardening measure (`android:exported`, `android:permission`, URI grants) — `spec/android/security/` §D
- Filing Play Console declaration forms, store listings, and the Data Safety questionnaire — operator-owned, out of repository scope
- Enumerating every permission constant the platform defines — the platform reference [R7] is authoritative; this spec covers the model and the families whose handling differs
- Device-administration, MDM, carrier-privileged, and system-app permission surfaces — not a target of this repository's skills

## Requirements

### A. The model a skill must hold before deciding anything

- **MUST** classify every permission it touches into one of the four platform types before reasoning about it, because the type determines the entire handling: **install-time normal** (`normal` protection level, granted at install), **install-time signature** (`signature`, granted only to apps signed with the defining certificate), **runtime** (`dangerous`, granted by the user through a system prompt), and **special** (`appop`, granted only through the Special App Access settings page and definable "only [by] the platform and OEMs") [R1]
- **MUST NOT** treat a runtime grant as a property of the app: it is revocable at any time from settings, may be granted only "Only this time" (Android 11+, for location, microphone, and camera) [R3], and is reset automatically when the app is unused for months under app hibernation — permissions reset on Android 11+, with jobs, alerts, notifications, and the cache also affected from Android 12 [R22]. It follows that a skill **MUST** check the permission immediately before each protected access and **MUST NOT** cache the result across a process lifetime — the platform states this as "don't assume that these permissions have been previously granted" [R1]
- **MUST NOT** build any logic on permission-group membership. Groups exist so the system can bundle prompts, and the documentation is explicit that "permissions can change groups without notice, so don't assume that a particular permission is grouped with any other permission" [R1]. A skill checks and requests each permission by name
- **MUST** keep a permission and a hardware feature distinct: a hardware-associated permission causes Play to filter the app off devices lacking the hardware, so any optional hardware **MUST** be declared `<uses-feature android:required="false">` and probed at runtime with `PackageManager.hasSystemFeature()` before use, with graceful degradation when absent [R5][R8]
- **SHOULD** record which permission model surfaces the user sees, because they change what "granted" means: the Privacy Dashboard timeline, the camera and microphone indicators, and the device-wide sensor toggles that hand the app a blank feed or silent audio rather than an error (Android 12+) [R14]

### B. Derivation — how the required set is determined

- **MUST** derive the set forward, from the app's intended behaviour, and **MUST NOT** derive it backward from what the manifest currently contains. The chain is **user-visible feature → device capability → concrete API call → the permission that API requires**, and a permission that cannot be traced to a named feature through that chain does not enter the set
- **MUST** establish the permission an API requires from an authoritative source rather than from memory: the API's own reference documentation, or its `@RequiresPermission` annotation — including its `allOf` / `anyOf` / `conditional` forms, which distinguish "all of these" from "any one of these" and are what the `MissingPermission` lint check enforces [R25]
- **MUST** run the alternatives gate of §C for every candidate permission before it is admitted, and **MUST** record the rejection reason when an alternative exists but does not suffice
- **MUST** read the **merged** manifest as a separate derivation input, because a dependency's manifest is merged into the app's and "when you include a library, you also inherit its permission requirements" [R1]. Any permission present in the merged manifest but absent from the derived set is a finding: it is either adopted with a written reason or removed per §D
- **SHOULD** treat a `SecurityException` at runtime, or a `MissingPermission` lint finding, as evidence that the derivation missed a call path — the fix is to re-derive that path, never to add the permission the exception names without tracing it to a feature
- **MUST** produce, as the operation's persistent output, a **permission ledger** with one row per permission in the final set, each row carrying: the permission name; its type per §A; the named user-visible feature that justifies it; the API call that requires it; the permission-free alternative that was considered and why it was rejected (or `none available`); the UI trigger point at which it is requested; the degradation behaviour when it is denied; and, where §G applies, the store-facing declaration obligation. A permission with an incomplete row is not admitted. The ledger **MUST** live at `project/permissions-ledger.md`, alongside the requirement and backend-requirement artifacts of `project/`, and a row **MUST** also record a permission that was deliberately *removed* (which library contributed it, why it was removed, and the removal marker used per §D), so a later dependency bump cannot reinstate it unnoticed
- **MUST** report a gap rather than deciding silently when the derivation reaches a capability whose permission requirement no spec and no primary source settles (per REQ-6 of `project/requirements/android-engineering-skills.md`)

### C. Alternatives first — the permission-free path

- **MUST** reject a permission wherever the platform offers a documented path that achieves the same user-visible outcome without it. Google's own framing is that permissions are to be minimized to reduce friction, in-app disclosure obligations, and privacy exposure [R2], and `spec/android/security/` §E already forbids requesting a permission where handing off to another app would do
- **MUST** apply the documented alternatives before declaring the corresponding permission [R2]:
  - **Photos and videos chosen by the user** → the Android photo picker, which grants temporary access to the selected items and needs no permission — never `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` for a "let the user pick" flow
  - **Documents and non-media files** → the Storage Access Framework; files the app itself created → app-specific storage or `MediaStore` — neither needs a storage permission
  - **Taking a photo or recording a video** → `ACTION_IMAGE_CAPTURE` / `ACTION_VIDEO_CAPTURE` handed to the system camera app, which needs no `CAMERA` permission. Note the documented trap: if the app *declares* `CAMERA` but has not been granted it, these intents raise a `SecurityException` — declaring the permission "just in case" actively breaks the permission-free path [R2]
  - **Scanning a code** → the Google code scanner, which needs no `CAMERA` permission; the full decision is owned by `spec/android/barcode-scanning/` §A/§G
  - **A one-off precise location** → the system location button (`ACCESS_FINE_LOCATION` avoided); an approximate need → `ACCESS_COARSE_LOCATION`; an infrequent need → let the user type an address [R2]
  - **Identifying an app instance** → an app-scoped identifier (`UUID.randomUUID()` persisted in app storage) or an installation identifier from the Firebase Installations API — never a hardware identifier, which `spec/android/security/` §E already forbids [R2]. The evaluating guide still names the Instance ID library for this, but that library's own documentation declares the Instance ID API deprecated in favour of Firebase Installations, so a skill **MUST NOT** add Instance ID to a new project [R34]
  - **Choosing a contact** → the Android Contact Picker (Android 17, API 37: `ContactsPickerSessionContract.ACTION_PICK_CONTACTS`, with the requested data fields passed as MIME types and a temporary read grant on the result), which the platform documents as "a privacy-preserving alternative to the broad `READ_CONTACTS` permission"; on lower API levels the classic `Intent.ACTION_PICK` on the contacts provider is the same permission-free hand-off with fewer options [R35]. `READ_CONTACTS` is admissible only for a feature that genuinely needs the address book as a whole, never for "let the user pick one"
  - **Pairing with a companion device** → Companion Device Pairing, which avoids the location and Bluetooth-admin permissions [R2]
  - **One-time passcodes, phone-number entry, call filtering** → SMS Retriever, the Digital Credentials API or Phone Number Hint, and `CallScreeningService` respectively, avoiding `READ_SMS` and `READ_PHONE_STATE` [R2]
  - **Pausing playback on an interruption** → an `onAudioFocusChange()` handler, not `READ_PHONE_STATE` [R2]
  - **Placing a call** → `ACTION_DIAL`, which needs no permission, rather than `ACTION_CALL` with `CALL_PHONE` [R2]
- **MUST NOT** declare a permission whose only justification is a third-party SDK's convenience; the SDK is audited and, where its requirement is disproportionate, replaced or its permission removed per §D — from the user's perspective the request comes from the app, not the library [R4]

### D. Declaring — conformance in the manifest

- **MUST** declare every permission in the final set with `<uses-permission android:name="…">` in the app manifest, and **MUST NOT** leave in the manifest any permission without a ledger row (§B) — including leftovers from removed features
- **MUST** bound a permission that is only needed below a certain API level with `android:maxSdkVersion`, so it is not requested where the platform no longer needs it [R5][R6] — the canonical cases being legacy storage and the legacy Bluetooth pair (`BLUETOOTH`, `BLUETOOTH_ADMIN` at `maxSdkVersion="30"`) [R11][R12]
- **MUST** apply `android:usesPermissionFlags="neverForLocation"` to `BLUETOOTH_SCAN` whenever the app can strongly assert it never derives physical location from scan results, and **MUST** then, *where the app still supports API 30 or lower and scans there*, bound `ACCESS_FINE_LOCATION` with `maxSdkVersion="30"` rather than carrying a location permission for a non-location feature. Where `minSdk` is 31 or higher the permission **MUST NOT** be declared at all: it could never apply, so it has no feature and therefore no admissible ledger row under §B. The documented cost of the flag is that some BLE beacons are filtered out of results [R11]
- **MUST** declare optional hardware `<uses-feature … android:required="false">` for every hardware-bound permission the app can live without, per §A [R5]
- **MUST**, for every foreground service, declare `android:foregroundServiceType` on the `<service>` element plus the base `FOREGROUND_SERVICE` permission *and* the type-specific `FOREGROUND_SERVICE_*` permission, and hold whatever runtime permission the type presupposes (for example `location` presupposes a granted location permission, `microphone` presupposes `RECORD_AUDIO`, `camera` presupposes `CAMERA`) [R13][R16]. Targeting Android 14+, a missing type raises `MissingForegroundServiceTypeException` from `startForeground()` and a missing `FOREGROUND_SERVICE_*` permission raises `SecurityException` [R16]
- **MUST** use `<queries>` to declare the specific packages or intent signatures the app interacts with, and **MUST NOT** declare `QUERY_ALL_PACKAGES` unless targeted queries provably cannot express the need — the permission is Play-restricted and requires approval [R17][R24]
- **MUST** remove a permission injected by a dependency that the app does not need, using the merge-rule marker in the app's higher-priority manifest — `<uses-permission android:name="…" tools:node="remove" />`, narrowed with `tools:selector="<library package>"` when only one library's contribution is meant [R18] — and **MUST** record the removal in the ledger so it is not silently re-added on the next dependency bump
- **SHOULD** define a custom permission only to restrict access to the app's own components, and then only at `android:protectionLevel="signature"`; a `normal`-level custom permission is granted to every app that asks and the naming-collision and definition-ordering pitfalls make weaker levels unsafe [R15]. Where such a permission guards a component, it is applied as `android:permission` on the `<activity>` / `<service>` / `<receiver>`, or as `android:readPermission` / `android:writePermission` on a `<provider>`, and the app **MUST NOT** rely on a broadcast receiver's permission check raising an error — a denied broadcast is simply not delivered [R15]. The surrounding component hardening (`android:exported`, `PendingIntent` immutability, explicit intents) stays with `spec/android/security/` §D
- **MUST NOT** ship `android:requestLegacyExternalStorage="true"` as a way to avoid the scoped-storage model; it is a documented temporary opt-out, not a design [R19]

### E. Requesting at runtime

- **MUST** implement the runtime request through the Activity Result APIs — `ActivityResultContracts.RequestPermission` for one permission, `RequestMultiplePermissions` for a set — and **SHOULD NOT** write new code against `ActivityCompat.requestPermissions()` with manual request codes, which the same documentation presents as the alternative rather than the recommendation [R3]
- **MUST** follow the platform's flow in order for every protected access: check with `ContextCompat.checkSelfPermission()`; if not granted, consult `ActivityCompat.shouldShowRequestPermissionRationale()`; show the in-context rationale when it returns `true`; launch the request; then branch on the result into either the protected work or the degraded path [R3]. The rationale's content and timing rules are owned by `spec/android/app-design-navigation/` §F
- **MUST** read `shouldShowRequestPermissionRationale()` together with the request history and never alone: on a not-granted permission it returns `false` in **two** different situations — before the first request (nothing to explain yet, so ask) and after the user has denied twice, when the system no longer shows the dialog at all [R3]. A skill **MUST** distinguish them by recording whether a request for that permission has already completed in this installation, and **MUST NOT** collapse them: treating first contact as a denial produces an app that explains a refusal the user never made and never shows the system dialog. In the genuinely **permanently denied** state the app **MUST** explain the state and offer a route to the app's settings page, and **MUST NOT** launch the request again in the hope of a dialog that will not appear
- **MUST** request incrementally and in context, never as a startup bundle: the platform requires foreground location to be granted before `ACCESS_BACKGROUND_LOCATION` is requested [R14][R10], and Play policy requires incremental, in-context requests as a condition of the sensitive-permission rules [R24]
- **MUST**, for special permissions, use their own path instead of the runtime flow: there is no system dialog, so the app checks with the permission's dedicated method (`AlarmManager.canScheduleExactAlarms()`, `Environment.isExternalStorageManager()`), shows a rationale that also explains what to do in settings, sends the user out with the permission's settings intent, and re-checks in `onResume()` on return [R4]
- **MUST** degrade rather than dead-end on denial: keep every unaffected feature working, make the specific unavailable feature legible instead of showing a generic blocking message, and accept the decision without nagging [R3]. A permission whose denial leaves no usable path is a derivation error in §B, not a UX problem
- **SHOULD** hold permission state in a state holder (ViewModel or an equivalent) and drive requests from user events rather than from composition, and **MUST**, where the Compose wrapper `rememberPermissionState` / `rememberMultiplePermissionsState` is used, keep the `@ExperimentalPermissionsApi` opt-in confined to one wrapper type — the API is documented as experimental and subject to change, and it cannot itself distinguish a first request from a permanent denial [R27]
- **MAY** proactively drop a permission the app no longer needs with `Context.revokeSelfPermissionOnKill()` / `revokeSelfPermissionsOnKill()` (Android 13+); the call is asynchronous and kills the app's processes, and clearing a group's user-visible state requires revoking every permission in that group [R3]
- **SHOULD** implement the data-access rationale activity (`VIEW_PERMISSION_USAGE`, and `VIEW_PERMISSION_USAGE_FOR_PERIOD` for the Privacy Dashboard entry) where the app accesses location, camera, or microphone in ways a user may not expect [R14]

### F. Families whose rules differ

- **Location** — `ACCESS_COARSE_LOCATION` (approximate) versus `ACCESS_FINE_LOCATION` (precise): declare fine only where precision is functionally required, and handle the case where the user grants approximate although fine was requested, upgrading only on an explicit user step. `ACCESS_BACKGROUND_LOCATION` is separately required from Android 10 (API 29), is requested only after a foreground grant, and is Play-restricted [R10][R24]. Continuous foreground access runs in a foreground service typed `location` [R10]
- **Media and storage** — for apps targeting Android 10+ scoped storage applies and the app's own media needs no permission. Access to *other apps'* media uses the granular `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` / `READ_MEDIA_AUDIO` (Android 13+), with `READ_MEDIA_VISUAL_USER_SELECTED` for the partial-access grant (Android 14+); on Android 16+ with partial access the app's own photos are pre-selected in the picker [R19][R21]. The granular permissions **do not exist below API 33**, so an app whose `minSdk` is lower **MUST** additionally declare `READ_EXTERNAL_STORAGE` for those devices — bounded at `maxSdkVersion="32"` so it is not carried where the granular set applies. Declaring only the granular set on such an app makes media access fail with a `SecurityException` on every device below 33 [R19]. `WRITE_EXTERNAL_STORAGE` is bounded with `maxSdkVersion="29"`; `MANAGE_EXTERNAL_STORAGE` is a special permission restricted by Play to core file-management functionality and **MUST NOT** be declared as a convenience [R19][R24]. `ACCESS_MEDIA_LOCATION` is required only for unredacted EXIF location metadata [R19]
- **Notifications** — `POST_NOTIFICATIONS` is a runtime permission from Android 13 (API 33) covering all channels including foreground-service notifications. Targeting API 33+, the app controls when the dialog appears and **MUST NOT** request it at first launch before the user has met the value it serves; targeting 32 or lower, the system shows the dialog on its own when a channel is created and an activity starts, which is a reason to target 33+ rather than a behaviour to rely on [R9]. Two further notification permissions exist and are **not** runtime permissions, which is exactly why they are easy to get wrong: **`USE_FULL_SCREEN_INTENT`** is declared at install time, but for apps targeting Android 14 (API 34) or higher Play revokes the default grant for every app that is not a calling or alarm app, the user can toggle it in settings, and it stays granted only for apps installed before the device updated [R29]. A skill **MUST** therefore treat it like a special permission at runtime — check `NotificationManager.canUseFullScreenIntent()` (API 34+, so guarded by an SDK-version check on any app whose `minSdk` is lower) immediately before use, degrade to an ordinary high-importance notification when it returns `false`, and send the user to `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` only on an explicit user step, never as a startup interruption [R29]. **`POST_PROMOTED_NOTIFICATIONS`** (Android 16) is declared in the manifest as a non-runtime permission and gates the promoted-ongoing surface; the user can switch the feature off per app, so the app **MUST** check `NotificationManager.canPostPromotedNotifications()` (API 36+, likewise guarded) before relying on promotion and **MUST** keep a working non-promoted notification for the same event. The settings route for that switch is `Settings.ACTION_APP_NOTIFICATION_PROMOTION_SETTINGS` (`android.settings.APP_NOTIFICATION_PROMOTION_SETTINGS`, API 36, input `Settings.EXTRA_APP_PACKAGE`; the reference warns that a matching activity may not exist, so the launch is guarded with a resolvability check) [R32] — the Live-Update guide's prose still names a differently-spelled constant that does not exist in the SDK, and a skill **MUST** use the SDK name, not the guide's [R30]. Both runtime checks are **SDK-guarded** by requirement, not by convention: `canUseFullScreenIntent()` is called only where `Build.VERSION.SDK_INT >= 34` and `canPostPromotedNotifications()` only where `>= 36`, and below those levels the declared permission is simply held (full-screen intent) or the surface does not exist (promotion). The guard *code* is owned by the notification-side channel templates (`spec/android/notifications-alerting/` §F and the skill that applies it); the permission derivation only records in the ledger row that the guard is required, and does not emit it. Which events legitimately reach either surface is derived in `spec/android/notifications-alerting/` §C — a full-screen intent only through its conversation gate (4, calls) and its interrupt gate (5, alarms), a promotion only through its ongoing-activity gate (2) — and this spec admits the permission only against that derivation
- **Bluetooth and nearby devices** — targeting Android 12+, `BLUETOOTH_SCAN`, `BLUETOOTH_ADVERTISE`, and `BLUETOOTH_CONNECT` are runtime permissions surfaced to the user as "Nearby devices"; declare only the ones the app's actual operations need, apply `neverForLocation` per §D, and bound the legacy pair at `maxSdkVersion="30"` [R11]
- **Exact alarms** — `USE_EXACT_ALARM` is granted automatically and not user-revocable, and is therefore restricted by Play to the narrow alarm-clock and calendar-style cases; `SCHEDULE_EXACT_ALARM` is user-granted and, on devices running Android 14 or higher, is **denied by default** for a newly installed app that targets Android 13 (API 33) or higher and is not a calendar or alarm-clock app — an existing grant survives the device upgrade, but a backup-and-restore transfer to Android 14 lands denied — so it requires a `canScheduleExactAlarms()` check plus a receiver for `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` to reschedule when the grant changes [R20][R36]. An exact alarm set through an `OnAlarmListener` needs neither permission, which narrows the cases further [R36]. A skill **MUST** first establish that the case genuinely needs exactness; scheduling, syncing, and periodic work use `setWindow()`, `setAndAllowWhileIdle()`, or WorkManager and need neither permission [R20]
- **Health and body sensors** — from Android 16, `BODY_SENSORS` and `BODY_SENSORS_BACKGROUND` are replaced by the granular health permissions of `android.health.connect.HealthPermissions`, whose manifest names carry the `android.permission.health.` prefix: `android.permission.health.READ_HEART_RATE` for the foreground read and `android.permission.health.READ_HEALTH_DATA_IN_BACKGROUND` for background access — there is no `READ_HEART_RATE_IN_BACKGROUND`, and a manifest that declares one declares nothing [R21][R37]. They also govern `Sensor.TYPE_HEART_RATE` and the `health` foreground-service type; the migration is required, and a mobile app using them must expose a privacy-policy activity or the permissions are revoked [R21]. An app whose `minSdk` is below 36 declares the legacy pair bounded at `maxSdkVersion="35"` alongside the new names and requests each set on the platform level that knows it [R37]. Play restricts health and fitness data to approved purposes [R24]
- **Package visibility** — from Android 11 the visible set is filtered; declare `<queries>` per §D and treat `QUERY_ALL_PACKAGES` as a last resort requiring Play approval [R17][R24]
- **Local network access** — Android 17 (API 37) enforces **Local Network Protection** for apps targeting 37 or higher: reaching a local-network address — raw sockets, TCP or UDP unicast, multicast and broadcast to local addresses, mDNS and SSDP queries, `.local` resolution, and the framework's own `NsdManager` — requires the new **runtime** permission `ACCESS_LOCAL_NETWORK` in the `NEARBY_DEVICES` group, so a user who already granted another `NEARBY_DEVICES` permission is not prompted again; an app targeting 36 or lower keeps the implicit grant that `INTERNET` carried, and loses it the moment its `targetSdk` moves to 37 [R31][R33]. Android 16 was the opt-in preview of the same restriction: there the compat flag `RESTRICT_LOCAL_NETWORK` (`adb shell am compat enable RESTRICT_LOCAL_NETWORK <package>`, reboot required) turned it on, and access was restored through `NEARBY_WIFI_DEVICES` because the dedicated permission did not exist yet [R21][R31]. The alternatives gate of §C applies before the permission is admitted: the platform documents two permission-free paths — the system service-discovery picker (`NsdManager` with a `DiscoveryRequest` carrying `DiscoveryRequest.FLAG_SHOW_PICKER`, which lets the user choose a service and hands the app that one connection) and the Output Switcher for media routing through Cast — and a skill **MUST** take one of them where the feature is "connect to a device the user picks" [R31][R33]. Because the enforcement version, the permission name, and the group are now settled, a skill **MUST NOT** re-derive them from memory; it **MUST** still verify at run time, against the primary source, whether anything has changed since this paragraph was written (a later release may widen the restricted operations or add pickers), and **MUST** treat every raw local-address socket use as within scope when it does
- **Nearby Wi-Fi devices** — its own family, distinct from local-network access and from Bluetooth: targeting Android 13 (API 33) or higher, the Wi-Fi APIs that manage connections to nearby devices — `WifiManager.startLocalOnlyHotspot()`, Wi-Fi Aware `attach()`/`publish()`/`subscribe()`, the Wi-Fi Direct `WifiP2pManager` discovery, connect, and group calls, and Wi-Fi RTT `startRanging()` — require the runtime permission `NEARBY_WIFI_DEVICES` instead of a location permission [R38]. It carries the same `android:usesPermissionFlags="neverForLocation"` assertion as `BLUETOOTH_SCAN` (§D), which removes the need for `ACCESS_FINE_LOCATION` on 33+; an app that also supports API 32 or lower keeps `ACCESS_FINE_LOCATION` bounded at `maxSdkVersion="32"` for those devices, and one whose `minSdk` is 33 or higher **MUST NOT** declare it for this feature at all [R38]. `NEARBY_WIFI_DEVICES` was the Android 16 stand-in for local-network access only during the opt-in preview above; on Android 17 the two are separate permissions with separate derivations, and a Wi-Fi-Aware or Wi-Fi-Direct feature does not by itself justify `ACCESS_LOCAL_NETWORK`, nor the reverse
- **Restricted by policy, not by API** — `READ_SMS` / call-log permissions require the app to be the default handler, and `AccessibilityService` use is bounded by Play policy; both are already forbidden as conveniences by `spec/android/security/` §E and are admitted here only through §G's declaration path [R24]

### G. The Play-policy boundary

- **MUST** hold the code to the two policy rules that constrain implementation rather than paperwork: a permission is declared only if it is "necessary to implement current features or services" that the app actually promotes, and access to sensitive data happens in context through incremental requests so the user can connect the request to what they asked for [R24]
- **MUST** keep a denial survivable at the product level, not only technically: policy requires that users who decline a restricted permission are not manipulated into granting it and retain a functional path [R24] — which is the same requirement as §E's degradation rule, arrived at from the policy side
- **MUST**, whenever the derived set contains a permission or capability that carries a store-side declaration obligation — the restricted permissions (SMS and call log, `MANAGE_EXTERNAL_STORAGE`, `QUERY_ALL_PACKAGES`, background location, broad photo and video access, health and fitness data, `AccessibilityService`) and, for apps targeting Android 14+, the foreground service types [R16][R24] — record that obligation in the ledger and report it to the operator as a handoff item. `USE_FULL_SCREEN_INTENT` belongs on that list, for apps targeting Android 14+, in a form of its own: Play removes the default grant from any app it does not judge to be a calling or alarm app, so declaring it is a claim about the app's category that the store reviews, not a local decision [R29]. Filing the declaration is the operator's act; leaving it undiscovered is the skill's failure
- **MUST NOT** interpret this section as authorisation to touch the store process: consistent with `spec/android/release-readiness/`, no skill edits store metadata, listings, or the Data Safety questionnaire

### H. Verification — proving the actual set

- **MUST** verify the effective permission set against the **merged** manifest, never the hand-written source manifest, because library contributions and merger-injected implicit permissions only appear there [R18]. The merger's decision log is written to `build/outputs/logs/manifest-merger-<variant>-report.txt`, and the merged manifest itself is produced under the variant's build-intermediates directory [R18]
- **SHOULD** confirm the shipped set from the built artifact with `apkanalyzer manifest permissions <apk>`, which prints exactly what the package declares [R26] — the strongest available check, since it sees the merge result rather than any intention
- **SHOULD** inspect the granted state on a device with `adb shell dumpsys package <pkg>`, reading the `USER_SET` flag as "denied once" and `USER_FIXED` as "permanently denied", and enumerate the platform's runtime permissions with `adb shell pm list permissions -d -g` [R3][R4]; the ADB mechanics themselves are owned by `spec/android/adb-workflows/`
- **MUST** run Android Lint with `MissingPermission` treated as an error, so a protected call without a check fails the build rather than the user's device [R25]. This is deliberately stricter than the general lint-severity rule of `spec/android/security/` §F, which is a SHOULD across the security check set: for this one check the spec corpus raises it to a MUST, because a missing permission check is the one defect that is invisible until a user hits it. The mechanics of wiring lint severities stay with §F
- **MUST** re-run the merged-manifest check after any dependency change, because a permission can enter the app without a source-manifest edit [R1][R18]

### I. Testing the permission paths

- **MUST** cover, for every permission in the ledger, at least three states as tests: granted, denied, and permanently denied — the denial branches are exactly the ones that ship broken, and `spec/android/barcode-scanning/` §J already requires this for its own surface
- **MUST** establish those states deterministically through ADB rather than by tapping dialogs: `pm grant` / `pm revoke` for the grant state, and `pm clear-permission-flags <pkg> <permission> user-set user-fixed` to return a permission to its never-asked state (with `pm set-permission-flags` to reach the denied-once and permanently-denied states) [R3][R9]
- **MUST** know the limits of `GrantPermissionRule` before relying on it: it only *grants*, it is ignored below API 23, and a permission granted this way applies to every test in the instrumentation run with no way to revoke it — attempting to revoke crashes the instrumentation process [R28]. It is therefore usable to get past a dialog in an unrelated test, and unusable as the mechanism for testing denial
- **MAY** pre-grant everything with `adb install -g` for hermetic runs that are not about permissions, per `spec/android/adb-workflows/` — but a run that does this **MUST NOT** be counted as coverage of the granted-state requirement above
- **SHOULD** exercise the special-permission return path (leaving to settings and re-checking in `onResume()`) at least once, since it has no system dialog and therefore no default-path coverage

## Acceptance Criteria

The criteria below are a deliberate representative rollup of §A–§I, not a 1:1 mapping; every requirement bullet above is normative on its own.

- [ ] A permission ledger exists at `project/permissions-ledger.md` with one complete row per declared permission — name, type, feature, API, alternative considered, declaration, trigger point, degradation, declaration obligation — plus a row per deliberately removed permission, and no permission is declared without one
- [ ] Every permission in the ledger was derived forward from a named user-visible feature, and the permission required by each API was established from its reference documentation or `@RequiresPermission` annotation rather than from memory
- [ ] For each declared permission, a permission-free alternative was considered and either adopted or rejected with a stated reason; no app takes a permission where the photo picker, a capture intent, the code scanner, the location button, SAF, Companion Device Pairing, the Contact Picker, the service-discovery picker, or an app-scoped identifier would have sufficed
- [ ] The merged manifest contains no permission absent from the ledger; every unwanted library-injected permission is removed with `tools:node="remove"` and the removal is recorded
- [ ] Every permission needed only below a given API level carries `android:maxSdkVersion`; `BLUETOOTH_SCAN` carries `neverForLocation` wherever the app does not derive location from scans; every optional hardware-bound permission is paired with `<uses-feature android:required="false">` and a runtime `hasSystemFeature()` check
- [ ] Every foreground service declares its `foregroundServiceType` plus the base and type-specific `FOREGROUND_SERVICE_*` permissions and holds the runtime permission that type presupposes
- [ ] Package visibility is expressed through `<queries>`; `QUERY_ALL_PACKAGES` appears only with a recorded justification that targeted queries cannot express the need
- [ ] Any custom permission is `signature`-level and enforced through the component's own permission attribute; no app ships `android:requestLegacyExternalStorage="true"` to avoid scoped storage
- [ ] Every permission from a family with its own rules is handled by that family's rule, not by the general one: location requested coarse-first and background-last, media through the granular permissions with partial access handled, `POST_NOTIFICATIONS` never at first launch, `USE_FULL_SCREEN_INTENT` and `POST_PROMOTED_NOTIFICATIONS` checked at runtime behind an SDK guard before use with a working degradation behind each and the promotion settings route launched through `Settings.ACTION_APP_NOTIFICATION_PROMOTION_SETTINGS`, Bluetooth declared per operation, `NEARBY_WIFI_DEVICES` carrying `neverForLocation` with no location permission on 33+, exact alarms justified as genuinely exact before either alarm permission is declared and `SCHEDULE_EXACT_ALARM` treated as denied by default on Android 14+, health permissions declared under their `android.permission.health.` names on Android 16+ with the privacy-policy activity present, `READ_CONTACTS` rejected wherever the Contact Picker suffices, and `ACCESS_LOCAL_NETWORK` derived only after the service-discovery picker and the Output Switcher were rejected — with the enforcement state re-checked against the primary source at run time
- [ ] Every runtime request goes through the Activity Result contracts and the check → rationale → request → respond → degrade flow, with the permission re-checked immediately before each protected access, never cached, and never inferred from another permission's grant through group membership
- [ ] The permanently denied state is distinguished from the never-asked state — both return `false` from `shouldShowRequestPermissionRationale()` — using the recorded request history, and is answered with an explanation plus a settings route; no code path re-requests a permission the system will no longer prompt for, and none treats first contact as a denial
- [ ] Background location is requested only after a foreground grant; no permission is requested as part of a startup bundle
- [ ] Every special permission is checked through its own API, requested via its settings intent behind a rationale, and re-checked in `onResume()`
- [ ] Denial of any single permission leaves the rest of the app usable, with the affected feature specifically identified rather than a generic block
- [ ] The shipped set is verified from the merged manifest and, where an artifact exists, from `apkanalyzer manifest permissions`; lint's `MissingPermission` is an error and the check is re-run after dependency changes
- [ ] Granted, denied, and permanently denied are covered by tests with the state established through ADB, and `GrantPermissionRule` is not used as the mechanism for denial coverage
- [ ] Every store-side declaration obligation implied by the derived set is recorded and handed to the operator, and no skill touches the store process itself

## Open Questions

Each open question is marked **parking-lot** — none blocks a skill from running this spec today, because each already has a working default fixed in the requirements above. Questions marked **closed** are kept for the trail: they record what was uncertain, and which requirement now carries the settled answer.

- **Compose permission API** (parking-lot). The Accompanist permission wrapper remains `@ExperimentalPermissionsApi` with no announced successor date [R27]; §E therefore requires containment rather than adoption or prohibition. Revisit when an official Compose permission API ships.
- **Local-network permission enforcement** — closed. An earlier revision could not confirm when the Android 16 opt-in preview would become enforcement; the Android 17 behaviour-change page and the local-network-permission guide now settle it (`ACCESS_LOCAL_NETWORK`, runtime, `NEARBY_DEVICES` group, enforced for `targetSdk` ≥ 37) and §F encodes that state [R31][R33]. What remains is only §F's standing instruction to re-check the primary source at run time, which is a requirement, not an open question.
- **Promoted-notification settings intent** — closed. The Live-Update guide's prose names `Settings.ACTION_MANAGE_APP_PROMOTED_NOTIFICATIONS`, which does not exist in the SDK; the `android.provider.Settings` reference and the AOSP source carry `ACTION_APP_NOTIFICATION_PROMOTION_SETTINGS` (`android.settings.APP_NOTIFICATION_PROMOTION_SETTINGS`, API 36, input `EXTRA_APP_PACKAGE`), which §F now fixes [R32]. The guide's prose is the stale party; a skill uses the SDK name.
- **Permission-set regression gate** (parking-lot). §H requires re-verification after dependency changes but stops short of requiring a checked-in baseline of the merged permission set that CI diffs against. Whether that gate is proportionate for a solo-developer project is unresolved; until it is, §H's manual re-verification stands.
