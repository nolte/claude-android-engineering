# Logging

Status: draft

## Context

Every skill in this repository generates or reviews code that logs, and logging is the one cross-cutting concern that is simultaneously a debugging tool, a performance cost, and a privacy liability. Google's own quality bar treats it as the latter: `Sensitive_Data_Logging` is a Core App Quality criterion, tested by exercising the app while watching the device log [R5]. This spec is the authoritative definition of how an app in this portfolio *produces* logs — the API it calls, the levels it uses, what a log line may contain, what a release build keeps, and how the rules are mechanically enforced.

The content is distilled from a research pass (August 2026) over three source classes: the official Android guidance (the dedicated Log-Info-Disclosure risk page, the security tips, the Core App Quality criteria, the R8 rule reference) and AOSP (`Log.java`, `liblog`, `logd`, the "Understand logging" page — read as source rather than as prose, because several widely-repeated claims turned out to be stale); the library ecosystem (Timber, kotlin-logging, kotlinx.coroutines, and the R8 optimizer's own string-builder passes); and measured evidence, of which exactly one peer-reviewed study exists for Android logging overhead [R24]. Three findings contradict the common literature and are stated here explicitly because skills would otherwise reproduce the folklore: the 23-character tag limit is historical and Google's own two sources disagree on when it ended [R1][R38], the `chatty` de-duplication that guides still cite as a spam safety net was deleted from AOSP in 2022 [R13], and the ProGuard rules published on Google's own security page are syntactically invalid [R3][R28].

Boundaries: *reading* logs — `adb logcat` invocation, buffers, filters, snapshot patterns, crash and ANR surfaces, `dumpsys`, Perfetto capture — is owned by `spec/android/adb-workflows/` §C/§D and is referenced here, never restated. This spec owns the producer side, which that spec's §C therefore no longer states. The prohibition on storing or transmitting sensitive data, and the data-classification scheme that decides what *counts* as sensitive, belong to `spec/android/security/` §A/§H; this spec applies that classification to log output and adds the redaction mechanics. The release-build gate that verifies no debug logging ships is `spec/android/release-readiness/` §B/§E; this spec owns the mechanism it verifies. That spec's §B also names the two mechanism options in one clause; where the two disagree on shrinker detail, §G here is authoritative and that clause is the summary. Telemetry-payload rules for performance events are `spec/android/perceived-performance/` §I. Crash and ANR *stability budgets* are `spec/android/release-readiness/` §C.

Readers: authors of this repository's Android skills (every skill that emits Kotlin), and the review agents that judge whether an app's logging is conformant.

## Goals

- Make logging a deliberate, layered decision instead of a reflex: one facade, one place where the platform is touched, one place where redaction happens
- Make the level of a log line mean something operationally, so that what survives into a release build is a considered set rather than an accident
- Make it structurally hard to log personal data, rather than relying on reviewer vigilance
- Keep the cost of logging off the frame budget and off the main thread's critical path
- Make every rule here mechanically enforceable — by lint, by a shrinker rule, by a test — and say which mechanism enforces which rule
- Give field diagnosis a path that does not depend on `logcat`, which a third-party app cannot read from a user's device

## Non-Goals

- Reading, filtering, or capturing logs from a device — `spec/android/adb-workflows/` §C/§D
- Choosing a crash-reporting or observability vendor; this spec fixes the obligations any such SDK must satisfy, not the product
- Backend log aggregation, retention schedules, and server-side pipelines
- Analytics and product telemetry as a discipline (event taxonomy, funnels); where analytics events carry payloads, `spec/android/perceived-performance/` §I and §C here both apply
- Tracing for performance analysis — `androidx.tracing`/Perfetto belong to `spec/android/perceived-performance/` §D/§E
- Defining what counts as personal or special-category data — `spec/android/security/` §H owns the classification this spec consumes

## Requirements

### A. The facade — what code actually calls

- **MUST** route every application log call through a single project-owned logging facade, and **MUST NOT** call `android.util.Log` (or `System.out`/`println`/`Throwable.printStackTrace`) directly anywhere outside that facade's implementation. The facade is the only place that knows about the platform, and therefore the only place that can enforce level policy, redaction (§C), and sink routing (§F) — Google's own guidance names this shape: "use debug flags and custom `Log` classes with easily configurable logging levels" [R4], and its redaction guidance goes further, requiring that "log printing should only be performed through a 'logs sanitizer' component that ensures all logs are sanitized before being printed" [R3]
- **MUST** keep the facade's *interface* free of Android types so that domain and data modules can log without depending on the platform, and **MUST** confine the Android-dependent implementation to a single module. A skill scaffolding a multi-module app puts the interface in the shared/core layer and the implementation behind it. This is what large production apps converge on: Signal routes everything through its own `Log` object and enforces it with a custom lint rule (`LOG_NOT_SIGNAL`, severity Error) that also rejects third-party loggers; DuckDuckGo standardises on Square `logcat` installed only on debuggable builds; Tivi uses Kermit behind a `core/logging` module [R42]
- **SHOULD** expose the facade as an injected dependency rather than a static object wherever the logging behaviour itself is under test or must differ per build variant; a static facade is acceptable in UI-layer code, where the alternative is threading a logger through composables. Whichever shape is chosen, it **MUST** be one shape per project, recorded with the decision
- **MAY** implement the facade over Timber rather than over `android.util.Log`: Timber's `Tree` mechanism is a ready-made sink abstraction, it defers `String.format` until after the level check, and it ships lint rules including `LogNotTimber` [R16]. A skill that chooses Timber **MUST** record that its last release is 5.0.1 and that it is stable-but-frozen, and **MUST NOT** treat `Timber.tag()`/`DebugTree` as free — see §D
- **MUST NOT** let the facade widen the platform's guarantees. Two are load-bearing and easy to get wrong: `Log.wtf()` is documented to log at `ASSERT` with the call stack and *may* add a DropBox report and/or terminate the process "depending on system configuration" — AOSP's own comment is that it "does not always cause a crash" [R1], so a facade **MUST NOT** present `wtf` as a reliable crash; and `Log.isLoggable`'s default level is `INFO`, overridable per tag with `setprop log.tag.<TAG> <LEVEL>` [R1]
- **MUST** treat the 23-character tag limit as historical and know that the two official sources disagree on when it ended: `Log.isLoggable`'s javadoc throws `IllegalArgumentException` for `tag.length() > 23` "for Nougat (7.0) and prior releases (API <= 25)", after which "there is no tag limit of concern" [R1], while the lint detector reports `LongLogTag` only when `minSdk <= 23` [R38], and the published check documentation states the rule with no API level at all [R9] — so lint goes quiet a platform release before the runtime throw actually stops. A project whose `minSdk` sits in that gap (24 or 25) gets no lint warning for a tag that can still throw at runtime, and **MUST** therefore keep tags ≤ 23 characters rather than relying on the check

### B. Levels — an operational contract

- **MUST** apply AOSP's retention semantics as the definition of each level, because they state what survives where: `ERROR`, `WARN`, and `INFO` — "these logs are always kept"; `DEBUG` — "these logs are compiled but stripped at runtime"; `VERBOSE` — "these logs are never compiled into an app except during development" [R2]
- **MUST** reserve `ERROR` for conditions that require someone to act, and **MUST NOT** log at `ERROR` an exception that the code goes on to handle successfully. An `ERROR` line that is not actionable trains every reader to ignore the level, which is the failure mode that makes production logs useless
- **MUST NOT** log-and-rethrow: an exception logged where it is caught and then rethrown is reported twice, once without the outer context. Log it where it is finally handled, or let it propagate
- **MUST** log a caught-and-handled exception at `WARN` at most, and **MUST** include what the code did about it — a handled failure whose log line does not say what recovery occurred is not actionable
- **MUST** treat `INFO` as the release floor: a line at `INFO` or above is one the project accepts shipping, with all of §C applying to it. `DEBUG` and `VERBOSE` are development-only and are removed per §G
- **SHOULD** keep `VERBOSE` for the tracing-style output that would drown the log at any other level, and gate it behind a runtime-togglable tag (`Log.isLoggable`, `setprop log.tag.<TAG> VERBOSE`) rather than a rebuild [R1]
- **MUST NOT** use `Log.wtf()` as an assertion mechanism in shipped code, per §A's terminate-or-not ambiguity; a genuine invariant violation belongs in the crash reporter as a non-fatal (§F)

### C. Content — what a log line may and may not contain

- **MUST NOT** write personal or sensitive user data to the system log or to an app-owned log. This is a Play quality criterion, tested by exercising every major feature while watching the device log: "No personal or sensitive user data is logged to the system log or an app-specific log" [R5]. AOSP states the floor bluntly — "Do not log Personally Identifiable Information (PII). This includes details such as: Email addresses, Telephone numbers, Names" — and warns that data need not be identifying to be sensitive: "though timezone info is not considered personally identifiable, it does give an indication of the approximate location of a user" [R2]. What counts as sensitive for a given project is the classification in `spec/android/security/` §H; class 1 (credentials and tokens), class 2 (personal data), and class 3 (special-category data) are all unloggable
- **MUST** treat the device log as a shared, readable resource rather than a private channel. Logs "are available to an application with the `READ_LOGS` permission", and although that permission has been restricted to privileged system apps since API 16, "Android supports an incredibly diverse set of devices whose pre-loaded applications sometimes declare the `READ_LOGS` privilege. As a consequence, logging directly to `logcat` is discouraged since it is more prone to data leakage" [R3][R4]. A third-party app cannot read another app's logs, and the platform prompts the user before granting even a foreground app access to all device logs [R2] — but neither fact makes the app's own output private
- **MUST NOT** log request or response bodies, headers carrying credentials, or serialized domain objects that have not been proven redaction-safe (`spec/android/backend-contract/` §B)
- **MUST** apply redaction at the sink or at the type, never at the call site alone: a rule that every author must remember at every call site fails silently the first time it is forgotten. The platform's own recommendation is the typed wrapper — a `ToMask<T>` whose `toString()` returns a constant and whose real value is reachable only through an explicitly named accessor, which "prevents accidental logging when an error is encountered" and "makes it more difficult for developers to invoke sensitive data" [R3]. The failure this guards against has a documented shape: in the Twitter (2018) and GitHub (2018) incidents alike, a logging statement sitting *upstream* of the hashing step turned a secure credential pipeline into a plaintext credential store — neither drew regulatory action, but both required a mass password reset [R42]
- **MUST** guard against the Kotlin `data class` auto-`toString()` trap, which is the most common way personal data reaches a log without anyone deciding to log it: a `data class` containing a personal field renders that field in full whenever the instance is interpolated, logged, or included in an exception message. Either the sensitive field is a masked wrapper type per the bullet above, or the class overrides `toString()`. A skill that generates a model type carrying class 1, class 2, or class 3 data **MUST** do one of the two — class 1 emphatically included, since a token or credential rendered by an auto-`toString()` is exactly the Twitter/GitHub failure above
- **SHOULD** prefer, among the four techniques the platform names, the ones that do not leak a residue: **tokenization** (log a vault token instead of the value), **redaction** (replace the whole field), and **filtering** (format-string substitution of non-constant values); **data masking** (partial, e.g. `XXXX-XXXX-XXXX-1313`) carries the platform's own warning — "Don't use data masking in cases where even releasing only a portion of the sensitive data can significantly impact security, such as when handling passwords" [R3]
- **SHOULD** follow the strictest form of the platform's advice where it is achievable — "Only log compile-time constants whenever possible" and, for anything that must remain in production, "remove non-constant variables from the log statements" [R3]. Where a variable must appear, it **MUST** be one whose domain is known and bounded (an enum, a state name, an HTTP status, a resource id), not free text that "might contain unanticipated information, including sensitive data, depending on the error triggered" [R3]
- **MUST** carry the identifiers that make a line correlatable — the screen or route, the operation, and any request/trace id propagated from the backend (`spec/android/backend-contract/`) — and **MUST NOT** use a non-resettable hardware identifier for correlation; the platform's recommended identifier for crash reporting and diagnostics is the Firebase installation id or the App Set ID, not the advertising id [R26]
- **MUST NOT** put sensitive data into the platform's crash side channels either: `ActivityManager.setProcessStateSummary()` carries its own instruction — "DO NOT include sensitive information/data (PII, SPII, or other sensitive user data) here. Maximum length is 128 bytes" [R15]

### D. Cost — the call site

- **MUST** treat the argument of a suppressed log call as work that still happens. AOSP's own javadoc is the authority: building `Log.v(TAG, "index=" + i)` means "the compiler uses a StringBuilder and at least three allocations occur… That means that if your log message is filtered out, you might be doing significant work and incurring significant overhead" [R1]
- **MUST** make the message lazy at every call site whose argument is not a compile-time constant. The only construction verified to be genuinely allocation-free on the disabled path is a project-local Kotlin `inline` function that performs the level check and only then evaluates an inlined message lambda, because inlining emits the interpolation *inside* the branch. A lambda that crosses a non-inline boundary — `kotlin-logging`'s `KLogger` interface, Compose's `SideEffect`, an SLF4J `Supplier` — still allocates a capturing closure before the check [R17][R30]
- **MUST NOT** assume a facade's format-args API is free: Timber defers `String.format` until after its level check, but the `vararg` array, the boxing of primitive arguments, and the spread-operator copies all happen at the call site before `prepareLog` is entered, and `DebugTree` captures a stack trace to derive the tag before the check runs [R16]. Timber solves the formatting cost, not the allocation cost
- **SHOULD** prefer a `BuildConfig.DEBUG` guard over `Log.isLoggable` where the intent is "never in release": `DEBUG` is constant-folded, so the whole branch is removed by the compiler, whereas `isLoggable` remains a real JNI call with a UTF-8 tag copy on every invocation. This is what the built-in lint check recommends [R7] — but the remedy needs a build feature the default project no longer has: since AGP 8.0 `android.defaults.buildfeatures.buildconfig` is **false**, so a project using this guard **MUST** set `buildFeatures { buildConfig = true }` explicitly [R40]
- **MUST NOT** log unconditionally inside a per-frame or per-item hot path — Compose composition and recomposition, `onDraw`, `onBindViewHolder` (whose budget is "much less than one millisecond"), or a scroll callback — at any level [R25]. `spec/android/long-list-scrolling/` §G and `spec/android/perceived-performance/` own the resulting measurements
- **SHOULD** size the expectation from the only measured study available: on a Pixel 2 XL, an instrumented run at roughly 850 log calls per second cost about 8 % response time and about 22 % battery against the same run with logging disabled [R24]. The study's own reading of its CPU columns is the useful part — the CPU is *idle* while logging, so the cost is not compute but the call's syscall and allocation overhead sitting on the calling thread
- **MUST** know that a log write is not disk I/O and does not block: `liblog` writes to the `/dev/socket/logdw` datagram socket with `SOCK_NONBLOCK` for every buffer except `security` [R11]. The corollary is the one that matters — under pressure the write returns `EAGAIN` and **the message is silently dropped** [R11], and AOSP advises against retrying because it "will only make the problem(s) worse and cause your application to temporarily drop to the logger daemon priority, BATCH scheduling policy and background task cgroup" [R12]
- **MUST NOT** rely on the `chatty` de-duplication that older guidance cites as a safety net against log spam. `ChattyLogBuffer` was deleted from AOSP (commit `91ee112`, "Remove chatty.", Elliott Hughes, 2022-09-20), landing in Android 14 and later; `logd.buffer_type` has defaulted to `serialized` since Android 12 [R13]. This rests on the AOSP tree rather than on documentation, because no Google-authored page records the removal: the deletion commit names the files, the author, and the date, and the current tree carries no `ChattyLogBuffer`. Spam now simply prunes the ring buffer faster, evicting the lines a diagnosis needs. The default buffer is 256 KiB, and the property overrides that would enlarge it are honoured only on `ro.debuggable` devices of automotive or desktop hardware type [R10]

### E. Concurrency and composition

- **MUST NOT** log a `CancellationException` as an error. Cancellation is normal control flow: "a coroutine that throws a `CancellationException` is considered to be cancelled normally", and these exceptions "are ignored by all handlers, so they should be used only as the source of additional debug information" [R19]. A `CoroutineExceptionHandler` never sees one, so application code must not manufacture the appearance of a failure [R19]
- **MUST** write the predicate in `Flow.onCompletion { cause -> … }` as `cause != null && cause !is CancellationException`, never `cause != null`: `onCompletion` "reports exception that occur both upstream and downstream and observe exceptions that are thrown to cancel the flow", so `cause` is non-null on every cancellation [R21]. A `take()` or `first()` produces one by design
- **MUST** rethrow a `CancellationException` that is caught by a broad `catch (e: Throwable)` around a logging site — "catching `CancellationException` can break the cancellation propagation. If you must catch it, rethrow it" [R20]; the documented shape calls `ensureActive()` before handling
- **MUST NOT** use `CoroutineName` or the `@name#id` thread-name suffix as the app's correlation mechanism: kotlinx.coroutines ships an R8 rule that permanently disables debug mode in optimized builds, so the identifier that appears in a debug log line is absent in release [R18]. Correlation **MUST** ride on a plain immutable `CoroutineContext.Element` carrying the id, which is inherited by child coroutines and survives every thread hop by construction
- **MUST NOT** rely on a thread-local (or SLF4J `MDC`) to carry logging context across suspension points: coroutines "are not bound to any particular thread", and a mutated thread-local's "updated value is lost on the next suspension" [R18]
- **MUST** place a `Flow` logging operator with awareness of where it runs: `flowOn` "affects only preceding operators" and, when it changes dispatcher, splits the chain into two coroutines, so an `onEach { log(…) }` above and below the same `flowOn` execute in different contexts [R21]
- **MUST** account for `repeatOnLifecycle` restarting collection: the block "will cancel and re-launch as the lifecycle moves in and out of the target state" [R22], so a one-shot-looking `onStart { log(…) }` fires once per STOP→START cycle — rotation, multi-window resize, app switch, screen off — not once per screen
- **MUST NOT** log from a composable function body. A composable "might be re-executed as often as every frame", recomposition may be skipped, discarded, or reordered, and "all composable functions should have no side-effects" — a log is a change visible to the rest of the app [R23]. A log belongs in a callback (`onClick`), in a `LaunchedEffect` keyed on the state that warrants it, or in the layer below the UI. `SideEffect { log(…) }` fixes only the correctness half: it "runs after every recomposition when invoked without any keys" [R23], so it does not bound the frequency

### F. Sinks — where a log line goes, and field diagnosis

- **MUST** route the facade's output per build variant rather than logging to one place unconditionally, and **MUST** keep the *verbose* `logcat` backend to developer builds: "We recommend that applications configure the `logcat` backend for developer builds only" [R3]. This bounds the volume, not the level floor: what §B admits at `INFO` and above may still reach `logcat` in release — that is what §G's stripping and §H's dex gate are measured against. A project that routes nothing at all to `logcat` in release satisfies this more strictly and **MAY** do so, provided §F's non-`logcat` diagnosis path still exists
- **MUST** provide a non-`logcat` path for anything the project needs to diagnose in the field, because a third-party app cannot read device logs from a user's device [R2] and `logcat` "cannot trigger alerts or be queried" [R3]. The platform's own alternative is explicit: "If you need more detailed logs, use internal storage and manage your own logs directly, instead of using the system log" [R3]. An app-owned log file is subject to every rule in §C — the Play criterion covers "the system log **or an app-specific log**" [R5] — and to the storage rules of `spec/android/security/` §A
- **MUST** read the previous process death from `ApplicationExitInfo` (API 30+) rather than inferring it, when the project needs to know why a session ended: `getHistoricalProcessExitReasons()` returns records most-recent-first, `getReason()` distinguishes crash, native crash, ANR, low memory, and user or system kills, and `getTraceInputStream()` yields the ANR trace — and, "beginning with API 31", a tombstone protobuf for a native crash [R14]. Three caveats **MUST** be carried with it: the retention is a ring buffer whose depth is *not* part of the public API contract; `REASON_LOW_MEMORY` is not reported on every device, so `ActivityManager.isLowMemoryKillReportSupported()` gates it; and `getDescription()` is "only intended to be human-readable" with "no guarantees that the format is stable across devices or Android releases", so no logic may branch on its text [R14][R15]
- **SHOULD** attach a bounded breadcrumb trail to a crash report — the last screens, the operation in flight, the feature-flag state — rather than expecting the reporter to capture the log. Breadcrumbs are subject to §C in full, and to whatever size and count limits the chosen SDK documents, which a skill **MUST** read and record rather than assume; the current spread is wide enough that a design cannot be portable across them by accident (Crashlytics: 64 kB of log per session, FIFO-evicted, 64 custom keys of 1 kB, and only the eight most recent non-fatals [R31]; Sentry and Bugsnag: 100 breadcrumbs by default [R32][R34])
- **MUST NOT** treat the crash SDK as the redaction point. Whether one exists is vendor-specific and Crashlytics — the most common choice — has **no** client-side scrubbing hook at all, so everything passed to it leaves the device unfiltered [R31]; Sentry offers `beforeSend`/`beforeBreadcrumb`/`beforeSendLog` [R33], Datadog an `EventMapper` [R35], OpenTelemetry an exporter customizer [R37]. §C's redaction therefore **MUST** live in the app's own facade (§A), which is the only seam present regardless of vendor
- **MUST** treat an SDK feature that captures `android.util.Log` automatically as a data-egress decision, not a convenience. Sentry's Gradle plugin rewrites `android.Log.*` calls by bytecode instrumentation — **enabled by default**, at `WARNING` and above, including calls inside bundled third-party libraries [R36] — and OpenTelemetry Android's `android-log` module does the same via Byte Buddy [R37]. Where such a feature is on, every pre-existing log call in the app *and its dependencies* becomes an upload, which §C governs and which no code review of the project's own sources would catch. A skill enabling it **MUST** record the decision and the minimum level
- **MUST** know when a report actually leaves the device before depending on it for incident response: Crashlytics batches and sends "the next time the app launches" [R31], whereas Sentry replays its envelope cache at init *and* on every connectivity regain [R33]. An SDK that only delivers on next launch **MUST NOT** be the sole sink where the project needs in-session delivery
- **MUST** record, where OpenTelemetry Android is chosen, that its artifacts are `-alpha` and that the project itself states they "will continue to have breaking changes" [R37]; two of its defaults also invert the usual expectation and **MUST** be set deliberately — disk buffering is **off**, and with no exporter configured the default exporters write to logcat and nowhere else [R37]
- **MUST** report a genuine invariant violation as a non-fatal to the crash reporter instead of `Log.wtf()` (§B), so that it is aggregated and countable rather than dependent on "system configuration" [R1]
- **SHOULD**, where the project needs to correlate an exit with what the app was doing, use `setProcessStateSummary()` for a compact state marker — subject to its 128-byte cap and its explicit no-PII instruction [R15] — rather than widening what is logged

### G. The release build

- **MUST** remove `DEBUG` and `VERBOSE` logging from the release build, and **MUST** do so by a mechanism recorded in the build, not by author discipline. Where the app processes personal data, this is not only hygiene: GDPR Art. 25(2) requires data-protection by default across "the amount of personal data collected, the extent of their processing, the period of their storage and their accessibility", and the EDPB applies that to logs explicitly — controllers "shall determine what personal data and length of storage is necessary for back-ups and logs" [R43]. Two mechanisms are available and they are not equivalent:
  - `-maximumremovedandroidloglevel <level> [<class_spec>]` is the purpose-built rule. It removes "Android logging statements (like `Log.w(...)` and `Log.isLoggable(...)`) at or below a certain log level" — the guards as well as the calls — using the level numbering VERBOSE 2, DEBUG 3, INFO 4, WARNING 5, ERROR 6, ASSERT 7; without a class specification it applies app-wide, and where several rules cover the same method "R8 uses the minimum level" [R6]. Removing both `DEBUG` and `VERBOSE` as this section requires means the level argument is **3**; `2` strips only `VERBOSE` and ships every `Log.d`
  - `-assumenosideeffects` is the older, blunter rule: R8 "can completely remove calls to such methods that have no return values or that return a fixed value" [R6]
- **MUST** prefer `-maximumremovedandroidloglevel` for `android.util.Log`, and **MUST** treat `-assumenosideeffects` as carrying the platform's own warning: "Assumptions instruct R8 to force further optimizations on your code, beyond what the code is analyzed to do. Use assumptions with caution, because forcing optimizations can break your app" [R6]. Where `-assumenosideeffects` is used, each removable method **MUST** be named individually rather than matched with a blanket `{ *; }` member wildcard, because such a rule also applies up the class hierarchy to inherited `java.lang.Object` members. Wildcards *within* a named method's signature — `public static *** v(...);` — are the documented working form and are not what this forbids
- **MUST NOT** copy the `-assumenosideeffects` block published on Google's Log-Info-Disclosure page [R3]: its member lines take the form `public static int v(TAG, "My log as verbose");`, which is not a valid ProGuard member specification. The working form specifies signatures, as in `public static *** v(...);` — the shape the ProGuard manual documents [R29] and that the empirical comparison uses [R28]
- **MUST** know what a shrinker rule does *not* reach: an argument expression with a real side effect (`Log.d(TAG, expensiveCall())`) survives, and a rule naming `android.util.Log` does not match a facade — a `Timber.d(…)` call is an ordinary static call and needs its own rule. A facade-based project **MUST** state how the facade's own release behaviour is achieved: a stripping rule for the facade class, or a release implementation that drops the low levels
- **MUST NOT** depend on either rule without the shrinker enabled: both are shrinker rules and do nothing otherwise. How it is enabled is version-gated and owned by `spec/android/release-readiness/` §A — `optimization { enable = true }` on AGP ≥ 9.3, `isMinifyEnabled = true` on earlier AGP — and on AGP ≥ 9.3 the rule file belongs in `src/<variant>/keepRules/*.keep`, not in a `proguardFiles` entry the newer DSL no longer reads. A skill **MUST** place the rule per the AGP version it scaffolds, not per the older shape
- **MUST NOT** assume the default configuration already strips logs. Neither the AOSP `proguard-android-optimize.txt` nor the file AGP actually generates at build time contains any `-assumenosideeffects` rule, any reference to `android.util.Log`, or a logging rule of any kind [R41]. The stripping rule is always something the project adds
- **SHOULD** enable R8's string-builder optimization to reach the now-dead concatenation left behind by a removed call. Modern R8 does this by analysis — its optimizer carries a dedicated `StringBuilderAppendOptimizer` with an escape-state dataflow analysis [R27] — whereas ProGuard required the assertion to be made explicitly with `-assumenoexternalsideeffects` on `java.lang.StringBuilder` [R29]. A project on a pinned older toolchain **MUST** verify rather than assume
- **MUST** verify the outcome against the built release artifact rather than against the rule's presence: `spec/android/release-readiness/` §E owns that gate, and the observable check is that a release build exercised across its major features emits nothing below `INFO` — which is also exactly how the Play criterion is tested [R5]

### H. Enforcement and verification

- **MUST** enable the lint check that targets the cost problem, because it is **disabled by default** (`setEnabledByDefault(false)` in the detector): `LogConditional` (Performance, Warning) flags an unconditional logging call and recommends surrounding it with `Log.isLoggable` or `BuildConfig.DEBUG` [R7][R38]. A project relying on lint for this rule **MUST** turn it on explicitly in `lint.xml` or the Gradle lint configuration, and **MUST NOT** mistake it for full coverage. Its reach is bounded twice over: the detector fires only for `Log.i`, `Log.d`, `Log.v`, and `Log.println` — never `w` or `e` — and only when the message argument does work that will not constant-fold [R38]; and because it matches `android.util.Log` calls, which §A confines to the facade's implementation module, in a conforming project it guards *that module* and never the call sites §D is actually about
- **MUST** leave the two enabled-by-default checks enabled: `LogTagMismatch` (Correctness, Error) — the tag *and* the level passed to `isLoggable` must match the log call they guard — and `LongLogTag` (Correctness, Error), with §A's rule about the gap it leaves [R8][R9]
- **SHOULD** add the opt-in security check that targets §C directly: `LogInfoDisclosure` (Security, Warning) is vendored by Google's Android 3P Vulnerability Research team and flags sensitive information logged to logcat, but it is **not** part of AGP — it requires `lintChecks("com.android.security.lint:lint:<version>")` [R39]. It is the only first-party mechanical check for the PII rule; no built-in equivalent exists. It carries §A's same blind spot — it inspects `android.util.Log` call sites, which live only in the facade module
- **MUST** name the mechanism that covers what the two platform checks above structurally cannot. Because §A confines `android.util.Log` to a single module, every rule about how the *rest* of the app calls the facade — §D's laziness, §C's content — needs a rule expressed against the facade's own API: a Detekt `ForbiddenMethodCall` on the facade's eager (non-lambda) overloads, or a project-local lint check registered against the facade class. The project **MUST** record which one it uses beside the facade decision (§A); without it, §C and §D rest on review alone and Goal 5 is not met
- **MUST** enforce §A mechanically rather than by review: a ban on `android.util.Log`, `System.out`, `println`, and `printStackTrace` outside the logging module, and **MUST NOT** expect lint to supply it: the catalogue contains no built-in check for `System.out`, `println`, or `printStackTrace` at all [R38]. The ban belongs in a Detekt `ForbiddenMethodCall`/`ForbiddenImport` rule or a project-local custom lint check; where Timber is the facade, its vendored `LogNotTimber` covers the `android.util.Log` half — a third-party check carrying the catalogue's own caveat that "the Android team may or may not agree with its recommendations", not an AOSP rule [R16][R39]. The rule **MUST** carry an allowlist for the facade's implementation module and nothing else. Where Timber is the facade this costs one line — `<issue id="LogNotTimber" severity="error" />` in `lint.xml`, as Element and AnkiDroid do. That it is cheap is the point: across seven large OSS Android apps, all seven have a logging abstraction but only two actually enforce it, and in three of the five failures the mechanism is present but left unconfigured [R44]. The abstraction is the easy part; the gate is what decays
- **MUST** make the logging facade testable and **SHOULD** assert on it where the log *is* the observable behaviour — a security-relevant event, a diagnostic that support depends on. An injected facade is asserted with a fake; a Timber-based facade is asserted by planting a recording `Tree` — Timber's author is explicit that this is the intended route ("There should be no reason to mock timber… If you want to assert logging occurred then plant a Tree which appends to an ArrayList"), and the projects that do assert on logs converge on exactly that shape rather than on Robolectric's `ShadowLog` [R44]. The rule is: never mock the logging facade, assert against a fake sink. This is a reason to prefer the injected shape (§A)
- **MUST** verify the release build against the built artifact with a command that actually works, because two obvious formulations both fail. `apkanalyzer dex packages --defined-only` never reports `android.util.Log` at all: it is a framework class, so an app's dex only ever *references* it and the flag filters references out [R44]. Matching the class line without that flag fails the other way — §B keeps `INFO` and above in the release build, so the class stays referenced in every conforming build and the gate would be permanently red. The check **MUST** therefore target the stripped *methods*: run `apkanalyzer dex packages <apk>` and match the referenced-method lines for `android.util.Log int v(` and `int d(` — the return type is `int`, not `void`, because these methods return a positive value when the message was loggable [R1] — whose presence means the stripping rule did not take
- **MUST** verify §C by execution, not by inspection: the conformance test is the Play criterion's own — exercise every major feature while watching the device log, and confirm no personal data appears [R5]. A skill that generates a logging surface **MUST** name this check in its verification step
- **SHOULD** record the project's log policy — which levels ship, which sinks exist per variant, what the redaction types are, and which rule strips what — as a durable artifact rather than as tribal knowledge, matching AOSP's own requirement that "an explicit policy must be set and followed… to decide how build types and release expectations impact log output" and that "log policy and acceptable details must be handled as part of security and privacy review before release" [R2]

## Acceptance Criteria

The criteria below are a deliberate representative rollup of §A–§H, not a 1:1 mapping; every requirement bullet above is normative on its own.

- [ ] No call to `android.util.Log`, `System.out`, `println`, or `printStackTrace` exists outside the logging module's implementation, and a mechanical rule (Detekt, custom lint, or `LogNotTimber`) enforces that with an allowlist covering only that module
- [ ] The facade's interface carries no Android types, the platform-dependent implementation lives in one module, and the static-vs-injected choice is one shape per project and is recorded
- [ ] Every level in use matches §B's contract: `ERROR` only where someone must act, no log-and-rethrow, handled exceptions at `WARN` or below and stating the recovery, and no `Log.wtf()` in shipped code
- [ ] No personal, credential, or special-category data (per `spec/android/security/` §H) reaches the system log, an app-owned log, a breadcrumb, or `setProcessStateSummary`; redaction is enforced by a masked wrapper type or a `toString()` override, not by call-site discipline
- [ ] Every generated model type carrying class 1, class 2, or class 3 data either wraps the sensitive field in a masking type or overrides `toString()` — the `data class` auto-`toString` path is closed
- [ ] Every log call whose message is not a compile-time constant is lazy — an `inline` guard or a facade whose level check precedes message construction — and no unconditional log call sits in a composition, `onDraw`, bind, or scroll path
- [ ] Cancellation is never reported as an error: `onCompletion` predicates exclude `CancellationException`, broad catches rethrow it, and no `CoroutineExceptionHandler` path fabricates one
- [ ] Correlation rides on a `CoroutineContext.Element` (or equivalent explicit propagation), not on `CoroutineName`, a thread-local, or `MDC`
- [ ] No composable body logs; logging happens in callbacks, keyed `LaunchedEffect`s, or below the UI layer
- [ ] `logcat` is a developer-variant sink only, and any diagnosis the project needs from the field has a non-`logcat` path whose storage obeys `spec/android/security/` §A
- [ ] Where the project reads previous-run exits, it uses `ApplicationExitInfo` with the low-memory support check, no logic branching on `getDescription()` text, and no assumption about retention depth
- [ ] Redaction happens in the app's own facade, not in the crash SDK; any SDK feature that auto-captures `android.util.Log` is either off or is a recorded decision naming its minimum level; the SDK's delivery timing is known to meet the project's incident-response need, and its breadcrumb limits are read from current vendor documentation rather than assumed
- [ ] The release build strips `DEBUG` and `VERBOSE` through a recorded shrinker mechanism — `-maximumremovedandroidloglevel` preferred, `-assumenosideeffects` with explicit signatures otherwise — the facade's own release behaviour is stated, minification is on, and the invalid block from [R3] is not present in the configuration
- [ ] A rule expressed against the facade's own API (Detekt or project-local lint) covers the call sites, and is recorded beside the facade decision; `LogConditional` is explicitly enabled; `LogTagMismatch` and `LongLogTag` are not disabled; tags are ≤ 23 characters or the suppression is deliberate and recorded
- [ ] A release build exercised across its major features emits nothing below `INFO`, verified against the built artifact rather than against the presence of a rule
- [ ] The project's log policy — shipping levels, per-variant sinks, redaction types, stripping mechanism — exists as a durable artifact

## Open Questions

- **Structured logging on Android.** `logcat` is a text pipe, so key-value structure buys correlation only once a line reaches a queryable sink; the platform's `EventLog` is documented as "system integrator diagnostic event logging" [R2] with no comparative guidance for apps, and no primary source recommends either shape for app code. *Default:* this spec fixes the *content* contract (§C) and leaves the encoding to the project, requiring only that correlatable identifiers be present.
- **Which crash-reporting SDK.** §F now fixes the *obligations* a vendor must satisfy and cites the August 2026 state of the five candidates, but it deliberately picks none: the choice turns on cost and on an existing observability stack, neither of which this corpus can decide. *Default:* a skill selects per project against §F's obligations, and re-reads the limits at scaffold time rather than trusting the numbers here, which are dated by construction.
- **Opt-in field logging and consent.** Enabling verbose diagnosis on a user's device, and uploading an app-owned log, are a processing activity with consent and retention consequences that no Android-side primary source addresses. *Default:* out of scope here; §F requires only that the path exist and obey §C. A project shipping such a flow needs a decision recorded outside this spec.
- **Sampling.** No primary source gives a defensible sampling rule for high-volume app events, and §D's measured evidence covers only the enabled-vs-disabled comparison [R24]. *Default:* none required; §D's hot-path prohibition and §G's stripping do the load-bearing work.
- **Verifying the `chatty` removal's reach.** The deletion commit, its author, and its date are recorded [R13] and the current AOSP tree carries no `ChattyLogBuffer`, but which shipping OEM builds still carry a backported de-duplication was not established. *Default:* §D forbids relying on it at all, which is correct either way.
