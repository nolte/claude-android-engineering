# Notifications and Alerting

Status: draft

## Context

Every app eventually has something to say: an order shipped, a sync failed, a download finished, a colleague replied, a background job needs a decision. The default reflex is to post a notification, and that reflex is where the damage starts. A notification is not a message the user receives — it is an interruption the app spends from a budget it does not own and cannot refill. The budget is all-or-nothing at the app level from Android 13 on: the user who is woken by a promotional notification at 07:00 does not mute that one event, they revoke `POST_NOTIFICATIONS`, and the delivery notification the app posts three days later never arrives. The second failure is the mirror image: an app that has something genuinely urgent to say, says it on a channel it created at `IMPORTANCE_LOW` two releases ago, and the user learns about the failed payment when they next open the app. Both failures are choices about *which channel carries which event*, made once, silently, at the moment a developer typed `NotificationManagerCompat.notify()`.

This spec fixes how the skills of this repository *decide* which alerting channel a business event gets, and how that decision is then *implemented* so the chosen channel behaves the way the classification promised. Its centre is a derivation — business event to classification to channel, with the cheaper channel rejected on evidence before the more expensive one is admitted — and a per-event record that makes the resulting set auditable instead of accumulated. The channel catalogue (§D) states for each option what it buys and what it costs, because the decision procedure in §C is only mechanisable if the trade-offs it weighs are written down. The mechanics that follow (delivery path, construction rules, permission and degradation, verification) are specified because a correctly classified event posted on a misconfigured channel is still a wrong app.

Provenance: desk research (August 2026) over the primary Android notification documentation (about-notifications, channels, build-notification, expanded styles, groups, badges, the notification runtime permission, conversations, bubbles, CallStyle, Live Updates, progress-centric notifications, time-sensitive notifications, and the notifications design guidance), the foreground-service documentation set (overview, launch, user-stopping, timeout, changes), the background-work decision guidance and the Doze/App-Standby guide, the Android 12, 14, 15, and 16 behaviour-change pages, the Firebase Cloud Messaging documentation (message priority, collapsible messages, receiving on Android, delivery understanding), the Wear OS bridging guide, the media-controls surface guide, the Compose Snackbar documentation, the `Notification.Builder` reference, and the Google Play policy on ads. Nothing here rests on a first-party measurement. Two positions are recorded as uncertain rather than hardened into requirements: the exact automatic-grouping and cooldown behaviour of recent platform versions, which the rendered documentation describes at a level of detail that does not support building on it (§F, §Open Questions), and the availability window of the Android 16 Live-Update surface on non-Google devices, which the platform documentation itself defers to OEMs [R12].

Boundaries: which in-app *component* renders an in-app message once §C has chosen the in-app path — snackbar versus dialog versus inline state, their action counts and duration rules — is owned by `spec/android/ui-components/` §A; this spec decides *whether* the message belongs in-app at all. Error-message wording, empty-state design, and the in-context permission-request timing rationale belong to `spec/android/app-design-navigation/` §F. The derivation, declaration, and denial handling of `POST_NOTIFICATIONS`, `USE_FULL_SCREEN_INTENT`, `POST_PROMOTED_NOTIFICATIONS`, the `FOREGROUND_SERVICE_*` family, and the exact-alarm permissions is owned by `spec/android/permissions/` — §G below states only what is notification-specific and feeds its rows into that spec's ledger. Notification icon artwork (alpha-only small icon, large-icon semantics) is owned by `spec/android/iconography/` §D. `PendingIntent` immutability, explicit intents, and component export rules are owned by `spec/android/security/` §D. Whether a wait the user is watching is honestly communicated and within budget belongs to `spec/android/perceived-performance/` (which indicator renders it is `spec/android/ui-components/` §A and `spec/android/app-design-navigation/` §F); this spec covers work the user has *stopped* watching. String externalisation and plural handling stay with `spec/android/localization/`. The shape of the server-side event contract that triggers a push — endpoint, payload schema, backend requirement capture — is owned by `spec/android/backend-contract/`. General ADB command mechanics stay with `spec/android/adb-workflows/`; where §H names a command that spec does not yet cover, that is an extension owed to it rather than a competing definition, and the ledger's test hook cites it. Test lanes stay with `spec/android/test-automation/`.

Readers: authors of this repository's Android skills that add, change, or audit any path by which an app tells a user something, and reviewers judging whether an app's alerting set is derived rather than accumulated. The operator is a secondary reader: §C's ledger is written *for* them, so it has to be legible without this spec in hand.

## Goals

- Make the alerting channel a *derived* result with a written trail — business event to classification to channel — instead of a reflex
- Force the cheaper, less intrusive channel to be considered and rejected on evidence before a more intrusive one is admitted
- State the trade-offs of every available channel explicitly, so the decision procedure is mechanisable and its outcomes are reviewable
- Protect the notification permission as a shared, revocable, app-wide resource that any single misuse destroys for every other event
- Make the chosen channel behave as classified: correct importance, category, grouping, lifecycle, and dismissal
- Fix the delivery path (local, scheduled, pushed) per event and refuse to treat any of them as guaranteed
- Guarantee that no information exists *only* in a notification — every event stays discoverable in the app
- Make the alerting set provable on a device and in tests, including the denied and blocked states

## Non-Goals

- Which in-app component renders an in-app message, and its action/duration rules — `spec/android/ui-components/` §A
- Error, empty, and form-state wording and design — `spec/android/app-design-navigation/` §F
- Permission derivation, declaration, request flow, and permanent-denial handling — `spec/android/permissions/`
- Notification icon artwork and per-surface icon formats — `spec/android/iconography/` §D
- `PendingIntent` and IPC hardening — `spec/android/security/` §D
- Progress feedback for work the user is actively watching — `spec/android/perceived-performance/`
- The backend event contract and its API surface — `spec/android/backend-contract/`
- Marketing campaign strategy, segmentation, and engagement optimisation — out of this repository's scope, and §C forbids the campaign notification outright
- Non-mobile surfaces as primary targets — Wear OS, Auto, and TV bridging is covered only as a consequence of a mobile notification (§F), not as an independent design surface

## Requirements

### A. The model a skill must hold before deciding anything

- **MUST** treat the ability to notify as a **revocable, app-wide, shared resource**, not a per-event capability: from Android 13 (API 33) notifications are off by default on new installs and a single denial silences every channel the app has, with only three qualifications: a media-session notification and a self-managed `CallStyle` call are exempt from the permission entirely, and a foreground service may still be *started* without it — its notification is then visible in the Task Manager only, not in the drawer [R8]. The permission itself covers every channel including the foreground-service one, exactly as `spec/android/permissions/` §F states; what survives a denial is the service, not its notification. It follows that every notification an app posts is spent against every future notification it will want to post
- **MUST** treat the user, not the app, as the owner of channel behaviour: after a channel is registered, its importance, sound, vibration, lights, and group membership can no longer be changed by the app — only its name and description can [R3]. The importance decision is therefore made **once per channel, permanently**, and is not a runtime knob
- **MUST NOT** assume a posted notification was delivered as posted. The platform re-ranks, defers, and dampens: heads-up presentation depends on channel importance and device state, the system groups notifications automatically once several arrive without an explicit group, recent versions reduce the intensity of repetitive notifications for a period, and Do Not Disturb suppresses whole classes by category [R1][R6]. A skill designs for the notification being seen late, silently, or bundled
- **MUST** hold the platform's own boundary as the first filter: a notification is for "brief, timely, and relevant information" the user needs while not in the app, and is explicitly wrong for cross-promotion, re-engagement, greetings, rating requests, background syncing the user never asked for, and recoverable errors the app handles by itself [R2]. Ads that simulate a system notification are a Play policy violation, not a design choice [R34]
- **MUST** keep the notification a *pointer*, never the only copy: any event worth a notification is also a state the app can render, and §G requires that path to exist independently
- **SHOULD** hold the delivery reality of the device in view before choosing a push-driven channel: in Doze, network access is suspended and jobs, syncs, and standard alarms are deferred to maintenance windows, and app-standby buckets throttle idle apps further [R26]

### B. Classifying the event — the input to the decision

- **MUST** classify every business event on these axes before any channel is considered, and **MUST NOT** name a channel first and justify it afterwards:
  - **Origination** — did the user start this (they tapped "upload"), did the app's own schedule start it (nightly sync), or did a third party start it (a colleague replied, a courier moved)
  - **Presence** — is the user in the app and looking at the affected surface, in the app elsewhere, or out of the app entirely. This is a runtime property, so the classification must state the behaviour for *each* case, not assume one
  - **Time sensitivity** — must the user act now (within a minute), soon (within the day), or never on a deadline
  - **Actionability** — does the event need a decision, an acknowledgement, or nothing at all
  - **Consequence of missing it** — safety, money, or data loss versus mild inconvenience versus none
  - **Continuity** — is this a point event, or an ongoing activity with a distinct start and end that the user tracks while it runs
- **MUST** answer the *silence gate* first: is there any user decision or user awareness that changes because of this event? An event that changes nothing the user would do differently gets no channel at all — it updates app state and waits to be found [R2]
- **MUST** classify a *recoverable* failure (a retry will fix it, the user cannot help) as silent by definition; only a failure whose resolution needs the user reaches §C at all [R2]
- **MUST** report a gap rather than deciding silently when an event's classification matches none of the substantive cases §C enumerates and is not a policy refusal either — §C's gap gate is where that report is raised, and it is a report about *this spec*, not about the app (per REQ-6 of `project/requirements/android-engineering-skills.md`)

### C. The channel decision — the procedure the automation runs

- **MUST** run the gates below **in order** and take the first one that matches. From gate 3 onward the ordering is cheapest-first, and that is the mechanism by which the cheaper channel wins where it suffices; gate 2 is the deliberate exception, placed early not because it is cheap — §D calls the foreground-service notification the heaviest option in the catalogue — but because an activity's continuity is a stable classification while presence is not (see its rationale below). A matched gate therefore proves that every gate above it was rejected, not that the outcome is inexpensive. Each gate's channel is specified in §D:
  1. **Silence gate** — §B's silence answer is "nothing changes" → no channel; the app updates its own state (§G's in-app path). This is the default outcome and needs no justification; every other outcome does
  2. **Ongoing-activity gate** — the event is a user-initiated activity with a distinct start and end that the user tracks while it runs (navigation, a ride, an active delivery, a workout, playback — but **not** a call, which is third-party-initiated and belongs to gate 4) → the **ongoing** family: a foreground-service notification where the app must keep running to do the work, `ProgressStyle` / a Live Update where the platform supports it and the activity is genuinely time-sensitive throughout, a media notification where a `MediaSession` exists. **MUST NOT** enter this gate for an activity the user did not start, for a far-future scheduled event, or for package tracking that needs no continuous attention [R12]. This gate sits *before* the presence gate deliberately: an ongoing activity is almost always started from the very screen it affects, so classifying it by presence would route exactly the activities this family exists for into the in-app path, and the decision is never revisited when the user leaves that screen a second later
  3. **Presence gate** — the event is a **point event** (§B continuity) *and* the user is in the app and on the surface it affects → **in-app surface only**; the component choice follows `spec/android/ui-components/` §A. A system notification for a screen the user is currently looking at is a defect, not a redundancy. Because presence is a runtime property and this gate is evaluated once, an event whose relevance outlives the current session is not decided here — it falls through to the gates below, which then also specify what happens when the user *is* present
  4. **Conversation gate** — the event is real-time interpersonal communication → the **conversation** family: `MessagingStyle` bound to a long-lived shortcut for messages, `CallStyle` for calls — and because a call is what the ongoing family's exclusion above hands here, this gate also owns the call's **full-screen intent**, which is one of the two categories the platform still grants it to and is checked at runtime per §F [R9][R16]. A messaging event **MUST NOT** be posted as a standard notification when the app can satisfy the conversation requirements, because the conversation surfaces (shade section, per-conversation user controls, bubbles) exist only for notifications that do [R9]
  5. **Interrupt gate** — missing the event within minutes has a safety, financial, or data-loss consequence **and** the user can act on it → a **high-importance notification** (heads-up). The gate is deliberately narrow: high importance is a claim that the event outranks whatever the user is doing, and the platform's own framing is that an unimportant notification disguised as urgent "can produce unnecessary alarm" [R2]. A **full-screen intent** is admitted here only for an **alarm**; the calling half of the platform's two-category restriction belongs to gate 4, which is where calls are decided, and both are checked at runtime before use [R16]
  6. **Await gate** — the event is relevant today but the user need not be interrupted → a **default- or low-importance notification**, silent where the user did not initiate the event
  7. **Ambient gate** — the event is a state the user may want to glance at repeatedly rather than an occurrence they must be told about → a **widget**, and a badge only where the app's own navigation carries it. A launcher badge is a consequence of a posted notification (§D) and therefore **MUST NOT** be named as the outcome for an out-of-app event; where the widget is the only implementable surface and the user has not placed one, the outcome is the silence gate's, not a notification [R7][R37]
  8. **Refusal gate** — the event is promotional, re-engagement-driven, or celebratory → **no channel**; the skill reports the request as out of policy rather than implementing it [R2][R34]
  9. **Gap gate** — an event that reaches this point has matched nothing above and is not a policy violation either: it is a case this spec does not cover. The skill **MUST** report it as a spec gap per §B and **MUST NOT** pick a channel by analogy
- **MUST** record, for every row whose matched gate produces a channel (gates 2 and 4 through 7), which cheaper gate *above* it was rejected and why — the chain is walked downward, so the cheaper outcome always sits earlier. Gates 1, 3, 8, and 9 record `n/a`: the silence and presence gates *are* the cheap outcome, and refusal and gap produce nothing by policy rather than by derivation
- **MUST** produce, as the operation's persistent output, a **notification ledger** at `project/notification-ledger.md`, alongside the permission ledger and backend-requirement artifacts of `project/`, with one row per business event carrying: the event name; its §B classification on all six axes; the gate that matched and the cheaper gate that was rejected, with the reason (`n/a` for a silence-gate row); the channel ID, user-visible channel name, and importance; the `setCategory()` value; the delivery path per §E; the behaviour for each presence case; the grouping and update key; the dismissal and cancellation rule; the degradation behaviour when the permission or channel is off; and the test hook per §H. A row whose outcome is **no channel** — the silence, presence, ambient-without-notification, refusal, and gap gates — carries `none` in every column that presupposes one (channel, category, delivery, grouping, dismissal, degradation) and stays complete: the classification, the matched gate, the in-app path, and the test hook are what make it auditable. An event with an incomplete row is not implemented
- **MUST** re-derive rather than patch when an event's classification changes: importance is immutable per channel (§A), so a change of importance is a **new channel**, and the ledger records the retired channel and the reason. Deleted channels remain visible to the user as a count in system settings, so channel churn is itself a cost [R3]
- **SHOULD** keep the channel set small and semantic — one channel per *type of event the user would want to control separately*, not one per notification site [R3]; **SHOULD** use channel groups only where the app genuinely has parallel account or profile scopes [R3]

### D. The channel catalogue — what each option buys and what it costs

Each entry states the gain, the cost, and the disqualifying case. §C's gates select among them; this section is why the gates are ordered as they are.

- **No channel (state only).** Gain: costs the user nothing, cannot be revoked, cannot be wrong. Cost: the user learns of the event only when they next open the app. Disqualifying: anything with a deadline the user must meet. Verdict: the default; every other entry must beat it on evidence
- **In-app transient or inline surface.** Gain: full control of presentation, no permission, no platform ranking, no revocation risk; the user is already looking. Cost: reaches nobody who is not in the app at that moment, and a transient surface is missed by a user whose attention is elsewhere on the screen; it also needs an explicit accessibility path for screen-reader users (§F). Disqualifying: the user is not in the app, or the event must survive being missed. Verdict: mandatory wherever the presence gate matches; component rules per `spec/android/ui-components/` §A
- **Badge (launcher dot, in-app navigation badge).** Gain: persistent, ambient, zero interruption, no sound; the count is available at a glance. Cost: carries no content, no timing, and no action; and it is a *consequence* of a posted notification on the launcher (suppressible per channel via `setShowBadge(false)`), so it is only independently available inside the app's own navigation [R7]. Disqualifying: the event needs content or action. Verdict: the companion of the ambient gate, never a channel on its own for out-of-app events
- **Widget.** Gain: persistent glanceable state on the home screen, user-chosen and therefore consented, no interruption budget spent. Cost: the user must have placed it; it is a surface the app must build and keep updated; it tells nobody anything at the moment the event happens. Disqualifying: time-critical events. Verdict: the right home for information the user wants to check repeatedly rather than be told once [R37]
- **Low- or minimum-importance notification (silent).** Gain: persists in the drawer until acted on, survives the app being closed, carries content and actions, and makes no sound; minimum importance keeps it out of the status bar entirely [R3]. Cost: spends the app-wide permission budget; competes with everything else in the drawer; easily unseen for hours. Disqualifying: the user must act within minutes. Verdict: the correct default for the await gate — most notifications that are worth posting are worth posting silently
- **Default-importance notification.** Gain: everything the silent variant offers plus a sound, which is the platform's own middle rung [R3]. Cost: an interruption in every context the user is in, including ones the app cannot see. Disqualifying: an event the user did not ask for and cannot act on. Verdict: for events the user initiated or subscribed to and expects a result from
- **High-importance notification (heads-up).** Gain: appears over the foreground app, with sound; the strongest attention the app can claim without the call and alarm surfaces [R1]. Cost: the highest revocation risk of any channel; misclassification here is what teaches users to turn an app off entirely [R2]. Disqualifying: anything without a minutes-scale consequence. Verdict: the interrupt gate only, and rarely
- **Grouped notifications with a summary.** Gain: keeps a multi-event stream legible, gives the user one dismissal target, and lets alerting be confined to the summary via `GROUP_ALERT_SUMMARY` [R6]. Cost: a group needs a summary notification and its own constant ID and update discipline; the platform's automatic grouping is version-dependent and not something to rely on [R6]. Disqualifying: a single, self-contained event. Verdict: mandatory as soon as an app can produce more than one notification of a kind at a time
- **Conversation notification (`MessagingStyle` + long-lived shortcut).** Gain: the dedicated conversation section, per-person avatars, direct reply, priority-conversation and bubble affordances, and correct ranking [R9]. Cost: requires publishing and maintaining long-lived sharing shortcuts and a `Person` model; shortcut removal loses user data and trust [R9]. Disqualifying: anything that is not interpersonal communication. Verdict: the only correct shape for messages; a chat app that posts standard notifications is misusing the platform
- **Bubble.** Gain: a floating, resumable conversation surface the user can keep on top of other apps [R10]. Cost: needs a resizable, embeddable activity plus conversation conformance; consumes screen space; entirely at the user's discretion — and the notification must still work when bubbles are disabled [R10]. Disqualifying: non-conversational content, and any flow that cannot fall back to a plain notification. Verdict: an opt-in enhancement of the conversation gate, never a dependency
- **`CallStyle` notification.** Gain: call-shaped layout with system-managed answer/decline actions, top-of-shade ranking, and exemption from the notification permission for self-managed calls [R8][R11]. Cost: only legitimate for actual calls; needs a foreground service (or colorization on older versions) to rank correctly [R11]. Disqualifying: anything that is not a call. Verdict: the call half of the conversation gate
- **Full-screen intent.** Gain: takes over the screen for an unmissable event [R14]. Cost: since Android 14 the permission is granted by default only to calling and alarm apps, others must send the user to a settings page, and the app must check `canUseFullScreenIntent()` before relying on it [R16]. Disqualifying: every non-call, non-alarm case. Verdict: effectively closed to ordinary apps — treat a design that needs it as a misclassification until proven otherwise
- **Foreground-service notification.** Gain: the app keeps running while the user is away, and the notification makes that visible [R20]. Cost: the heaviest option in the catalogue — a service type declaration plus its permission set, background-start restrictions since Android 12, a user-facing Stop affordance in the Task Manager since Android 13, user-dismissible ongoing notifications since Android 14, and a six-hour-per-day budget for `dataSync` and `mediaProcessing` after which `onTimeout()` fires and failure to stop crashes the app [R15][R22][R17][R23]. Disqualifying: work that can be deferred — that is WorkManager's job [R25]. Verdict: only where the work must continue *and* be user-noticeable now
- **Live Update / `ProgressStyle` (progress-centric, promoted ongoing).** Gain: promoted placement at the top of the drawer, on the lock screen, on the always-on display, and as a status-bar chip, with a journey rendered as segments and points [R12][R13]. Cost: needs `POST_PROMOTED_NOTIFICATIONS`, an explicit promotion request, an ongoing flag, a content title, and one of the permitted styles; forbids custom layouts, group summaries, colorization, and minimum importance; the surface is uncollapsible and OEM behaviour may differ [R12]. Disqualifying: anything not ongoing, not user-initiated, and not continuously time-sensitive — the documentation names package tracking, chat, ads, and upcoming calendar events as wrong [R12]. Verdict: the strongest ongoing surface, available to a narrow and well-defined class of activity
- **Media notification (`MediaStyle` + `MediaSession`).** Gain: the system media carousel with transport controls derived from player state, and exemption from the notification permission [R8][R31]. Cost: requires a real media session and correct metadata. Disqualifying: non-media use. Verdict: mandatory for playback, useless elsewhere
- **Out-of-band channels (email, SMS, server-side push to another device).** Gain: reaches a user who has revoked notifications or does not have the app open on this device. Cost: outside the app's control and outside this repository's scope; the contract for them belongs to `spec/android/backend-contract/`. Verdict: a backend requirement to be captured, never a client-side workaround for a denied permission

### E. Delivery — how the event reaches the device

- **MUST** choose the delivery path from exactly three options for every ledger row that carries a channel, and record it: **local** (the app itself is running and knows), **scheduled** (the app knows in advance when to tell the user), or **pushed** (only the server knows). A no-channel row records `none` per §C and skips the rest of this section
- **MUST** implement scheduled delivery through WorkManager for anything deferrable, and reserve `AlarmManager` for events whose *time itself* is the user-visible point (an alarm, a reminder the user set) — the exact-alarm permissions and their justification requirement are owned by `spec/android/permissions/` §F, and the platform's own decision guidance puts WorkManager first [R25]
- **MUST NOT** treat push as guaranteed delivery. FCM stores a bounded backlog per device — one hundred non-collapsible messages, after which all stored messages are discarded and the device is told the limit was hit — and at most four distinct collapse keys concurrently [R28]. A skill therefore **MUST** design the client so that a missed message is recoverable by a state sync on next foreground, and **MUST** treat the push as a hint to synchronise rather than as the source of truth
- **MUST** use FCM **data messages** wherever the app must control the resulting notification — channel assignment, grouping, localisation, styling, or any of §F's rules — because a notification message delivered while the app is backgrounded is rendered by the SDK into the system tray without the app's code running at all [R29]. A notification message is admissible only for an event whose presentation genuinely needs no app decision
- **MUST** reserve `priority: high` for messages that produce a user-visible notification or an immediate user-facing interaction: FCM monitors the correlation over a rolling window and may deprioritise the app's messages or take over notification display when high-priority messages fail to produce notifications [R27]. Normal priority is the default for background sync and is delayed in Doze [R26][R27]
- **MUST** keep `onMessageReceived()` work inside its short execution window and hand anything longer to WorkManager — expedited work for high-priority messages, an ordinary request otherwise [R29]
- **MUST NOT** route a notification tap through a service or broadcast receiver that then starts an activity: from Android 12 that trampoline is blocked, and the `PendingIntent` must target the activity directly [R15]. The destination is the content the notification is about, reached as a deep link with a plausible synthetic back stack per `spec/android/app-design-navigation/` §E
- **SHOULD** compose user-visible notification text on the device from an event key and parameters rather than accepting a rendered string from the server, so it is localised and plural-correct per `spec/android/localization/`; where a server-rendered string is unavoidable, the ledger row records it and the language it was rendered in
- **SHOULD** verify the app's behaviour under Doze and app standby for every pushed or scheduled row, since deferral there is the normal case rather than an edge case [R26]

### F. Constructing the notification — conformance rules

- **MUST** build every notification through `NotificationCompat.Builder` against a channel created before first use; on Android 8.0 (API 26) and higher a notification without a channel is not shown at all and the failure is logged rather than raised [R3]. Legacy devices additionally need `setPriority()` set consistently with the channel importance [R3]
- **MUST** set `setCategory()` from the platform's category constants on every notification — it is what the system uses for Do Not Disturb filtering and ranking, and it is the only machine-readable statement of what the notification *is* [R2]
- **MUST** set lock-screen visibility deliberately per row: `VISIBILITY_PRIVATE` with a `setPublicVersion()` for anything whose content is sensitive on a locked screen, `VISIBILITY_SECRET` where even the presence is sensitive; the public version is also what the system shows during screen sharing on recent versions [R4][R18]. Any content the app treats as sensitive under `spec/android/security/` §A — the data it keeps out of logs and external storage — never appears in a notification's visible text either, and the ledger row names the classification it applied
- **MUST** update rather than re-post: the same notification ID with `setOnlyAlertOnce(true)` for progress and status changes, since re-posting alerts again and rapid updates are throttled by the system [R4]
- **MUST** cancel a notification that has gone stale — the event was handled elsewhere, the offer expired, the user acted in the app — because a drawer full of irrelevant notifications is what precedes an app-wide block [R2]. `setAutoCancel(true)` covers the tap case, `setTimeoutAfter()` the self-expiring case, and an explicit `cancel(id)` the rest [R4]
- **MUST** group with an explicit group key **and** a group summary as soon as the app can produce more than one notification of a kind concurrently, rather than relying on the platform's automatic grouping, whose behaviour varies by version and device [R6]. Promoted Live Updates are the one exception and **MUST NOT** be grouped: the promotion contract below forbids a group summary, so concurrent Live Updates of a kind stay separate promoted notifications [R12]; the summary uses a constant ID and is updated with the group, and alerting is confined per `setGroupAlertBehavior()` [R6]
- **MUST** keep actions within the platform's limits and semantics: at most three, none duplicating the tap action, each a `PendingIntent` that is immutable unless a direct reply genuinely requires mutability, per `spec/android/security/` §D [R4]. Where the app is a messaging app, direct reply via `RemoteInput` is expected rather than optional [R2]
- **MUST NOT** ship custom notification layouts (`setCustomContentView()` and its siblings): from Android 12 the system re-decorates them into a standard template with a reduced collapsed height, and the Live Update surface rejects them outright [R15][R12]
- **MUST**, for a foreground-service notification, carry a stop affordance and let the notification appear when the work does — the platform may defer the notification by ten seconds on Android 12 and higher, which is correct for short work and wrong for work the user is waiting to see, where `setForegroundServiceBehavior(FOREGROUND_SERVICE_IMMEDIATE)` applies [R20][R35]. The service **MUST** handle being stopped from the Task Manager (Android 13+) and its notification being dismissed (Android 14+) without leaving orphaned work [R22][R17]
- **MUST**, for a Live Update, satisfy the full contract before requesting promotion — ongoing flag, content title, a permitted style, no group summary, no colorization, no minimum-importance channel — check `canPostPromotedNotifications()` before relying on the surface, provide a delete intent, and **MUST NOT** re-post a Live Update the user dismissed [R12]
- **MUST**, for a conversation notification, publish a long-lived dynamic sharing shortcut with `Person` data and bind it with `setShortcutId()` / `setShortcutInfo()`; without it the notification is not a conversation notification on Android 11 and higher, whatever style it uses [R9]
- **SHOULD** keep the title short and the body scannable — the design guidance puts the title under 30 characters and the preview text under 40, and forbids repeating the app name, which the system already renders [R2]
- **SHOULD** set `setLocalOnly(true)` for notifications that are meaningful only on the device that produced them, and otherwise let bridging to a paired Wear OS device happen, controlling it by bridge tags rather than disabling it globally [R32]
- **SHOULD NOT** rely on accessibility announcements to convey an event to screen-reader users: `announceForAccessibility()` and `TYPE_ANNOUNCEMENT` events are deprecated as of Android 16 in favour of live regions, pane titles, and error semantics [R38]. An in-app surface chosen at §C's presence gate carries an accessibility path selected on that basis

### G. Permission, user control, and degradation

- **MUST** derive `POST_NOTIFICATIONS` through `spec/android/permissions/` §B and request it in context — tied to the first moment the user opts into an event class that needs it, never at first launch, and never as part of a startup bundle [R8]. `spec/android/permissions/` §F already states this rule; the notification-specific addition is that the *rationale names the event class*, so the user is agreeing to something concrete
- **MUST** check `areNotificationsEnabled()` before relying on the channel at all, and additionally read the target channel's `getImportance()` before treating a notification as delivered attention — a channel the user set to `IMPORTANCE_NONE` accepts `notify()` calls and shows nothing [R3][R8]
- **MUST** implement, for every ledger row, an in-app path to the same information that does not depend on the notification being seen: a state in the app the user can find, a list, a badge, or an inbox. A notification is a pointer to app state, so an app whose event exists only as a notification loses that event permanently on denial or dismissal
- **MUST** degrade rather than nag when notifications are off: the affected features keep working through the in-app path, the app explains what is unavailable at the point where it matters, and it offers a route to the system settings — `ACTION_APP_NOTIFICATION_SETTINGS` for the app level and `ACTION_CHANNEL_NOTIFICATION_SETTINGS` for a specific channel [R3]. The app **MUST NOT** re-prompt into a dialog the system will not show; the permanent-denial rules of `spec/android/permissions/` §E apply unchanged
- **SHOULD** expose the app's own notification preferences where the channel model alone is too coarse (frequency, quiet hours, per-topic subscription), and keep them consistent with the system channels rather than duplicating them [R2]
- **MUST NOT** work around a denial: no out-of-band delivery, no alarm-based substitute, no full-screen intent as a replacement for a permission the user withheld. A denial is a decision, and §D's out-of-band entry is a backend requirement, not a client workaround

### H. Verification and testing

- **MUST** cover, for every ledger row that carries a channel, at least these states as tests: **granted and delivered**, **permission denied**, and **channel blocked or set to no importance** — the last two are exactly the paths that ship broken, and both must land on §G's in-app path. A no-channel row (§C) has none of those states; its test hook proves the other half instead — that the in-app path renders the event's state — and a row whose gate was refusal or gap has no test hook at all, only its recorded classification
- **MUST** establish those states deterministically through ADB rather than by tapping system UI, using the permission-flag commands owned by `spec/android/adb-workflows/` and specified for this permission in `spec/android/permissions/` §I (`pm grant` / `pm revoke` / `pm clear-permission-flags` / `pm set-permission-flags`) [R8]
- **MUST** exercise, for a foreground-service row, the user-stop path (`adb shell cmd activity stop-app <package>` simulates the Task Manager Stop, which sends no callback and is only detectable afterwards via `ApplicationExitInfo` with `REASON_USER_REQUESTED`) and, where the type is `dataSync` or `mediaProcessing`, the timeout path — the compat flag `FGS_INTRODUCE_TIME_LIMITS` and the `device_config` timeout keys make the six-hour budget testable in minutes [R22][R23]
- **MUST** verify deferred-delivery behaviour for every scheduled or pushed row under Doze and app standby (`dumpsys deviceidle force-idle` / `unforce`, `am set-inactive <package> true|false`), asserting that the event is not lost — only late [R26]
- **SHOULD** assert the posted notification from an instrumented test through UI Automator, which is the only supported framework that sees system UI outside the app under test [R36]; where the assertion target is the app's own decision rather than the system rendering, prefer testing the channel-selection function directly as a pure unit
- **SHOULD** verify the deep-link destination of every notification's content intent as a navigation test per `spec/android/test-automation/`, since a notification that opens the wrong screen fails silently in production
- **MUST NOT** count a manual observation on one device as coverage for a row whose classification claims a time-critical consequence

## Acceptance Criteria

The criteria below are a deliberate representative rollup of §A–§H, not a 1:1 mapping; every requirement bullet above is normative on its own.

- [ ] A notification ledger exists at `project/notification-ledger.md` with one complete row per business event — classification on all six axes, matched gate, rejected cheaper gate with reason (`n/a` for a silence-gate row), channel and importance, category, delivery path, per-presence behaviour, grouping key, dismissal rule, degradation, and test hook, with `none` in every channel-presupposing column of a no-channel row — and no notification is posted from code without one
- [ ] Every event was classified before a channel was named, and every event that changes nothing the user would do differently, or whose failure the app recovers from by itself, has no channel at all
- [ ] No point event is posted as a notification for a surface the user is currently looking at, and no ongoing activity is demoted to the in-app path because it happened to start on that surface; every ledger row states its behaviour for all three presence cases
- [ ] High importance appears only on rows whose consequence of being missed is safety, money, or data loss within minutes; no promotional, re-engagement, greeting, or rating notification exists anywhere in the app
- [ ] Full-screen intents appear only in a calling or alarm surface, guarded by a runtime `canUseFullScreenIntent()` check with a settings route as the fallback
- [ ] Every ongoing activity uses the ongoing family correctly: a foreground service only where work must continue and be user-noticeable, with a stop affordance, Task-Manager and dismissal handling, and timeout handling for `dataSync` / `mediaProcessing`; a Live Update only where the activity is user-initiated, ongoing, and continuously time-sensitive, satisfying the full promotion contract and never re-posted after dismissal
- [ ] Every interpersonal message notification uses `MessagingStyle` bound to a long-lived shortcut, and every call uses `CallStyle`; bubbles, where used, still work as ordinary notifications when disabled
- [ ] Every channel is created before use with a deliberately chosen, permanent importance; a change of importance is implemented as a new channel with the retirement recorded, not as an in-place edit
- [ ] Every notification sets a category and a deliberate lock-screen visibility, with a public version wherever the content is sensitive; no sensitive content appears in visible notification text
- [ ] Multi-event streams are grouped with an explicit group key and a constant-ID summary, except for promoted Live Updates, which stay ungrouped; no app relies on automatic grouping
- [ ] Stale notifications are cancelled, updates reuse the notification ID with `setOnlyAlertOnce`, and no custom notification layout is shipped
- [ ] No notification tap passes through a trampoline; every content intent targets its activity directly and lands on the content with a plausible back stack
- [ ] Push-delivered rows use data messages wherever the app controls presentation, reserve high priority for user-visible outcomes, recover missed messages by state sync on next foreground, and hand long work to WorkManager
- [ ] Every scheduled row runs on WorkManager unless the event's own time is the user-visible point, in which case it uses `AlarmManager` with the exactness justification `spec/android/permissions/` §F requires
- [ ] No notification carries more than three actions, none duplicates the tap action, and every action's `PendingIntent` is immutable except where a direct reply requires otherwise
- [ ] Notification text is composed on the device from keys and parameters, or the ledger records why it is server-rendered
- [ ] Every event is reachable in the app independently of its notification, and the app degrades to that path — with a settings route, without re-prompting — when notifications are denied or the channel is off
- [ ] Granted, denied, and channel-blocked states are covered by tests for every channel-bearing row, with the state established through ADB, while a no-channel row's hook proves its in-app path instead; foreground-service rows additionally cover user-stop and, where applicable, timeout; scheduled and pushed rows are verified under Doze and app standby

## Open Questions

Each question is marked **parking-lot** — none blocks a skill from running this spec today, because each already has a working default fixed in the requirements above.

- **Live Update availability** (parking-lot). The platform documentation states that OEMs may enforce additional criteria for promoted ongoing notifications and defers to their documentation [R12]. This spec therefore requires a runtime capability check and a working non-promoted fallback rather than encoding an availability claim. Revisit when device-side behaviour is measurable across the operator's target devices.
- **Automatic grouping and cooldown detail** (parking-lot). Recent platform versions group and dampen notifications automatically, but the rendered documentation describes the thresholds too loosely to build on [R1][R6]. §F therefore requires explicit grouping and treats dampening as an unobservable given. Revisit if the platform documents the exact behaviour.
- **Ledger placement for multi-module apps** (parking-lot). The ledger sits at `project/notification-ledger.md` for the whole app, mirroring the permission ledger. Whether a modularised app should keep per-feature ledgers that a build step aggregates is unresolved; until it is, the single-file rule stands.
- **Notification analytics** (parking-lot). This spec requires no delivery or engagement telemetry, and `spec/android/perceived-performance/` §I would constrain any that is added. Whether an app should track post-versus-open rates to detect a channel that has stopped working for its users is unresolved; the ledger's classification is the current substitute.
