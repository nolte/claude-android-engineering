# QR and Barcode Scanning

Status: draft

## Context

Scanning a code looks like a solved problem — a camera, a decoder library, a string — and it is the string that makes it dangerous. A scanner is an input channel that lets a stranger who printed a sticker put arbitrary bytes into an app, and the second half of every scanning defect lives after the decode, not before it. The first half is physical: whether a code is decodable at all is decided by pixels per module, quiet zone, and focus, and an app that gets those wrong produces a viewfinder that simply never fires, with no error to debug. Between the two sits a platform decision most projects make by habit rather than on evidence — Google's ready-made scanner needs no camera permission at all, and reaching for CameraX plus a detector when it would have sufficed buys a permission prompt, a privacy indicator, and a pipeline for nothing.

This spec fixes how this portfolio's skills build and judge a scanning surface: which of the three access paths is the right one, what makes a code decodable in the first place, how the camera pipeline must be configured so the detector gets an image it can use, how the scan act is presented and confirmed, what must happen to a decoded payload before anything acts on it, how the surface stays usable without a camera, and how a code this portfolio *generates* stays readable by the scanners this portfolio *builds*.

Provenance: desk research (August 2026) over the ML Kit barcode-scanning and code-scanner documentation, the CameraX guides and release notes, the Android permission, accessibility, and deep-link security documentation, the OWASP MASTG platform-interaction chapter, the FBI/FTC/NCSC advisories on malicious codes, Denso Wave's QR documentation, W3C WCAG understanding documents, and the ZXing sources. No requirement here rests on a first-party measurement — unlike `spec/android/uvc-microscope/`, nothing below was hardware-verified. Three load-bearing facts that the rendered reference pages would not yield were read directly from AOSP source instead and are cited as such: the analysis-resolution default [R13][R14], the dial-versus-call distinction [R26], and the confirmation-haptic contract [R35]. Where a widely repeated number has no traceable normative source, this spec says so and refuses to make it a requirement (§B, §Open Questions).

Boundaries: general deep-link, intent, WebView, and input-validation hardening is owned by `spec/android/security/` §D, permission minimalism and the Data Safety declaration by its §E; in-context permission UX, error-state wording, and the response-time feedback semantics by `spec/android/app-design-navigation/` §F, deep-link routing by its §E; the wait-indication matrix, the message-surface choice (dialog vs snackbar vs bottom sheet), and button emphasis by `spec/android/ui-components/` §A/§B; external UVC cameras by `spec/android/uvc-microscope/`, which explicitly leaves built-in cameras to ordinary guidance; device, log, and trace mechanics by `spec/android/adb-workflows/`; test lanes and the emulator-versus-device split by `spec/android/test-automation/`. General camera work that is not scanning — photo capture, video, gallery pipelines — has no spec yet; see §Open Questions.

Readers: authors of this repo's Android skills who add or review a scanning or code-generating surface, and reviewers judging whether such a surface is conformant.

## Goals

- Make the access-path decision mechanical, so the no-permission path is taken wherever it suffices and rejected on evidence where it does not
- Make decodability a budget that is computed rather than hoped for, in both directions — reading a code and printing one
- Keep the camera pipeline from being the reason detection fails, starting with the default resolution that silently defeats it
- Draw one hard trust boundary at the decode, so no scanned byte reaches an interpreter, an intent, or a network call unexamined
- Make the scan act confirmable, repeatable, and interruptible, with the decoded content shown before anything happens to it
- Keep the surface operable for a user who cannot aim a camera at all
- Make a generated code readable by the scanners this corpus builds, including the encoding trap where that is not automatic
- Make scanning testable without a print shop

## Non-Goals

- Dedicated hardware scanners (Zebra, Honeywell, rugged imagers) and their keyboard-wedge or intent output such as DataWedge — a separate product surface with its own SDK contract
- Symmetric coverage of every symbology: this spec is QR-first, and treats 1D families and the other 2D matrices only where their rules differ (§B)
- Photo capture, video recording, and gallery pipelines built on CameraX — no spec owns these yet (§Open Questions)
- External UVC and microscope cameras — `spec/android/uvc-microscope/`
- Server-side validation of a scanned identifier (inventory lookups, ticket redemption); this spec ends at the app's trust boundary and states what must hold before the value is sent
- Barcode print-quality grading as a production process (ISO/IEC 15415 verification equipment and grades)
- OCR and text recognition, which is a different ML Kit API with different constraints

## Requirements

### A. Access-path decision

- **MUST** choose deliberately between three paths and record which one and why: the **Google code scanner** (`com.google.android.gms:play-services-code-scanner`, `GmsBarcodeScanning`), an **in-app scanner** (CameraX plus ML Kit barcode scanning), or a **GMS-free decoder** (ZXing). The choice is not a style preference — it determines whether the app holds the camera permission at all
- **MUST** default to the Google code scanner where the interaction is a bounded, one-shot "scan a code and come back with a value", because it is the only path that scans "without requiring your app to request camera permission" [R3]: camera access happens inside Google Play services, which returns only the result. Reaching for an in-app scanner where this suffices contradicts `spec/android/security/` §E, which forbids requesting a permission where handing off to another app would do
- **MUST** use the in-app CameraX plus ML Kit path only for a stated reason that the code scanner cannot serve — a custom or embedded viewfinder, continuous scanning, an overlay drawn on the live frame, scanning combined with another camera feature, or an operational requirement to work where the scanner module cannot be downloaded. Google's own guidance points the same way: "For more complex use cases that require a custom UI, we recommend using the ML Kit Barcode Scanning API directly" [R3]
- **MUST NOT** treat the code scanner as unconditionally available: it "uses an unbundled library that must be downloaded before use" [R3], so the module may be absent on first run. A skill **MUST** pre-request it — install-time `com.google.mlkit.vision.DEPENDENCIES` metadata or an explicit `ModuleInstallClient` request — **and MUST**, independently of that, handle the not-yet-available case with a real state, never a silent no-op [R3][R7]. Pre-requesting narrows the window; it does not close it, so the handled state is required either way
- **MUST** decide the ML Kit model supply explicitly on the in-app path and record it: the bundled model (`com.google.mlkit:barcode-scanning`) ships in the APK for "about 2.4 MB" and works immediately, the Play-services model (`com.google.android.gms:play-services-mlkit-barcode-scanning`) costs "about 200 KB" but must be downloaded — and until that download completes, "inference requests will fail" [R1][R7]. A first-run scan that silently fails is this decision made by accident
- **MUST** treat API level 23 as the floor for all three Google artifacts [R1][R3] and **MUST NOT** carry the API-21 figure that circulates in secondary summaries; the vendor documentation states 23. Which options exist at all is version-bound — auto-zoom and `enableAllPotentialBarcodes` arrived in specific releases [R8] — so a skill **MUST** check an option against the version the project actually resolves rather than against this spec's dated observation
- **SHOULD** add a GMS-free decoder only where the target set genuinely includes devices without Play services, and then **MUST** declare it as a second, explicitly bounded code path rather than a silent fallback — two decoders reached by accident produce two different accuracy profiles for the same feature. ZXing has no Play-services dependency, which is exactly why it is the fallback [R46][R47]
- **MUST NOT** adopt `com.journeyapps:zxing-android-embedded` as a new dependency without recording it as a known-stale choice: its last release is 4.3.0 from October 2021 and it bundles ZXing core 3.4.1 while core itself has moved on [R52][R53] (S). Where a ZXing path is required, the maintained `com.google.zxing:core` driven from the project's own CameraX pipeline is the conformant construction
- **MUST NOT** present ZXing as equivalent in detection quality: the only quantified public comparison is vendor-published and shows the gap appearing on adversarial imagery (blurred, damaged, dense, multi-code) while clean single-code scans reach parity for every engine tested [R54] (S). The honest statement is "adequate for clean codes, weaker on damaged ones", not "the same"

### B. Decodability budget

- **MUST** size the input so "the smallest meaningful unit of the barcode should be at least 2 pixels wide, and for 2-dimensional codes, 2 pixels tall" [R1]. This is the one hard, vendor-stated number in this area and it governs both directions: it decides the capture resolution when reading and the printed module size when generating
- **MUST** compute the pixel budget from the symbology rather than guessing: an EAN-13 image "should be at least 190 pixels wide", a PDF417 "would ideally be at least 1156 pixels wide" [R1], and a QR symbol needs twice its module count per side — which at version 40's 177×177 modules is 354 px across the symbol alone, before the quiet zone [R40]
- **MUST** provide "a higher resolution image, such as 1280x720 or 1920x1080" where codes are scanned at a distance, and **MUST NOT** exceed roughly 2 megapixels for real-time scanning, which is the documented ceiling beyond which latency is paid for nothing [R1]
- **MUST** honour the quiet zone as a property of the symbology, not a margin taste: a full-size QR symbol requires **4 modules** on all sides, a Micro QR symbol **2 modules** — Denso Wave states the contrast directly: "QR Code requires at least a four-module wide margin around a symbol, whereas a two-module wide margin is enough for Micro QR Code" [R42]. 1D quiet zones are expressed in multiples of X, the narrow-bar width (Code 128 and ITF-14 around 10X, EAN-13 asymmetric at 11X left and 7X right) [R55] (S), and **MUST NOT** be compared numerically with a module count — they are different units
- **MUST** keep the standard polarity — dark modules on a light background — for any code the project generates or specifies, and **MUST NOT** rely on inverted (light-on-dark) codes being read: inversion is a decoder-side accommodation, not a symbology feature. ZXing exposes it as an opt-in `ALSO_INVERTED` decode hint [R47], and usability research states the rule plainly: do not invert QR-code colours [R39] (S)
- **MUST NOT** build a required capability on any of ML Kit's documented exclusions, each of which fails silently rather than reporting an error: **QR codes generated in ECI mode are not recognised**; codes using FNC2, FNC3, or FNC4 encoding are not recognised; 1D barcodes with a single character are not recognised; ITF codes under six characters are not recognised and the format is "known to be flaky due to absence of checksum" [R2]
- **MUST** treat Data Matrix as a special case on the in-app path: the code "must intersect the center point of the input image. Consequently, only one Data Matrix code can be recognized in an image" [R1]
- **MUST NOT** exceed the documented yield of "no more than 10 barcodes per API call" when designing a multi-code surface [R2]
- **MUST NOT** design for Structured Append (multi-part QR), Micro QR, or rMQR on the ML Kit path: ML Kit's supported-format list names none of the three [R2]. Micro QR and rMQR are real, standardised symbologies [R42][R43] — they are simply outside what the decoders this corpus uses document as supported. Whether any given decoder handles Structured Append at all was **not** established from a primary source in this research pass, and that unresolved state is itself the reason not to build on it
- **MUST NOT** turn the widely repeated sizing folklore into a requirement: the "code size ≈ scanning distance ÷ 10" ratio and the "never smaller than 2 cm × 2 cm" floor appear only in marketing material with no traceable normative source, and the second is separately asserted by usability research [R39] (S). Where a physical size must be fixed, it **MUST** be derived from the 2-pixels-per-module rule and the target device's capture resolution, with the folklore figures usable only as a sanity check
- **MUST NOT** cite ISO/IEC 18004 for a contrast threshold: symbol structure and error correction are 18004's subject, while print-quality contrast grading belongs to the separate ISO/IEC 15415 [R44][R45]. Both are paywalled, so a skill **MUST** report the gap rather than quote a number it cannot verify

### C. Camera pipeline (in-app path)

- **MUST** set an explicit `ResolutionSelector` on `ImageAnalysis` and **MUST NOT** accept its default: CameraX binds a default selector bounded at VGA with a 4:3 strategy and `FALLBACK_RULE_CLOSEST_HIGHER_THEN_LOWER` [R13][R14], and the configuration guide states the same as "The default target resolution setting is 640x480" [R12]. Against §B's budget that default is the single most common reason a viewfinder never fires on a small or distant code
- **MUST NOT** use the deprecated `setTargetResolution`/`setTargetAspectRatio` pair in new code, and **MUST NOT** set both a target aspect ratio and a target resolution on one use case — doing so "throws an `IllegalArgumentException` when building the configuration object" [R12]
- **MUST** keep the backpressure strategy at `STRATEGY_KEEP_ONLY_LATEST`, which ML Kit's own integration guidance requires so a slow decode drops frames instead of queueing them [R1][R11]
- **MUST** close every `ImageProxy` on every path including the error path, and **MUST NOT** call `close()` on the wrapped `Media.Image` — the docs warn this "would break the image sharing mechanism inside CameraX" [R11]. An unclosed proxy stalls delivery under `KEEP_ONLY_LATEST` and stalls the whole camera device scope under `STRATEGY_BLOCK_PRODUCER`, which presents as a frozen viewfinder rather than as a leak
- **MUST** pass `imageProxy.imageInfo.rotationDegrees` into `InputImage.fromMediaImage(...)` — only 0, 90, 180, and 270 are accepted [R1] — and **MUST** keep `targetRotation` current for a surface that rotates, via an `OrientationEventListener` or a `DisplayListener` [R17]. A rotation mismatch degrades detection without producing an error
- **MUST** keep the analysis output format at the `YUV_420_888` default rather than opting into `RGBA_8888`: ML Kit consumes YUV directly [R1], and the RGBA path makes CameraX convert every frame [R11]
- **MUST NOT** hand-compute the mapping from detection coordinates to preview coordinates. `Barcode.getBoundingBox()`/`getCornerPoints()` are in analysis-image space, and the supported constructions are `MlKitAnalyzer` with `COORDINATE_SYSTEM_VIEW_REFERENCED` via `CameraController` [R16], or the `CoordinateTransformer` supplied by `CameraXViewfinder` on the Compose path [R19] (S). Corner points are explicitly "not necessarily a rectangle" because of perspective distortion [R5], so an overlay drawn from a bounding box alone will visibly lie
- **MUST** budget the analyzer against the frame interval — the documented target is "less than 32ms for 30 fps" [R11] — and **MUST NOT** perform decoding work on the main thread
- **MUST** gate every torch affordance on `CameraInfo.hasFlashUnit()`: without a torch, `enableTorch()` "causes the returned `ListenableFuture` to complete immediately with a failed result and sets the torch state to `TorchState.OFF`" [R12], so an ungated button is a control that does nothing
- **SHOULD** wire ML Kit's zoom suggestion rather than inventing a zoom heuristic: `setZoomSuggestionOptions` makes "the library suggest zooming the camera if the barcode is too far away or too small to be detected", the callback always arrives on the main thread, and the bound **MUST** come from `CameraInfo.getZoomState().getValue().getMaxZoomRatio()` — the documentation warns that without `setMaxSupportedZoomRatio` "the library may produce an unbounded zoom ratio" [R6][R1]. The suggested ratio is applied through `CameraControl.setZoomRatio` [R12]
- **SHOULD** offer tap-to-focus through `startFocusAndMetering` built from `previewView.meteringPointFactory`, noting that the action auto-cancels after 5 seconds unless overridden and that not every device supports all metering modes or multiple regions [R12]
- **SHOULD** host the viewfinder with `CameraXViewfinder` from `androidx.camera:camera-compose` on a Compose surface rather than wrapping `PreviewView` in an `AndroidView`, and **MUST** record the CameraX version the choice was made against — observed 2026-08-12: stable 1.6.1, alpha 1.7.0-alpha03 [R19]. On a View surface, `PreviewView` defaults to `PERFORMANCE` implementation mode and `FILL_CENTER` scale type [R15]; a cropping scale type **MUST NOT** be allowed to hide part of the frame the user is being asked to aim with
- **MUST** respect the use-case binding limit — one `Preview` and one `ImageAnalysis` — and **MUST** treat a combination that works at low resolution but not at high as a real constraint rather than a device quirk [R18]
- **SHOULD** check the detector's published known issues against the project's own CameraX version before debugging a device-specific failure: the pairing has broken before, with barcode SDKs below a stated version failing on some devices from `camera-camera2:1.0.0-beta08` onward [R9]. A skill **MUST NOT** treat that dated entry as current, only as evidence that this interface is a place defects live

### D. Detector configuration

- **MUST** restrict the accepted formats with `setBarcodeFormats` to exactly what the feature consumes: "Reducing the number of supported formats will make the barcode scanner faster" [R4], and an unrestricted scanner also accepts symbologies the feature has no meaning for, which is an input-surface problem as much as a performance one. The same option exists on the code-scanner path [R10]
- **MUST** use `rawValue` for anything the app acts on and `displayValue` only for display: `displayValue` "may omit some of the information encoded in the barcode", while `rawValue` returns the value "as it was encoded" [R5]. Binary payloads **MUST** go through `rawBytes`, which is null when the bytes cannot be determined
- **MUST** branch on `valueType` rather than pattern-matching the raw string when the payload is structured, and **MUST** treat every parsed structure as untrusted per §F regardless of how well it parsed [R5]
- **MUST** close the `BarcodeScanner` when the surface is torn down [R1]
- **MUST NOT** assume frame-to-frame stability: the vendor documentation states that scanning "from a sequence of streaming video frames, the recognizer might produce different results from frame to frame" [R1]. A continuous scanner therefore **MUST** define its acceptance rule — the value it acts on and when — rather than acting on the first frame that decodes
- **SHOULD** enable `enableAllPotentialBarcodes()` together with the zoom suggestion where codes are small or far: it "returns all potential barcodes when enabled, even if they cannot be decoded", with `rawValue`/`rawBytes` null but a bounding box present, so the app can guide or zoom toward a code it has seen but not read [R4]. Any UI built on it **MUST** distinguish "seen" from "read"
- **SHOULD** enable `allowManualInput()` on the code-scanner path, which is disallowed by default [R10] — it is the same accessibility obligation as §H's manual entry, already implemented
- **SHOULD** enable `enableAutoZoom()` on the code-scanner path, which is disabled by default [R10]

### E. The scan act

- **MUST** decide and record whether the surface is one-shot or continuous, and **MUST** make a continuous scanner suppress duplicates so one physical code is not consumed repeatedly. No vendor source states a debounce interval, so the value **MUST** be recorded at its definition site rather than scattered as a literal (§Open Questions)
- **MUST** show what was decoded and require an explicit user action before anything acts on it (§F). The decoded value, not a summary of it, is what the user is being asked to judge
- **MUST** confirm a successful scan through more than one channel and **MUST NOT** make audio the only one — a deaf user gets nothing from a beep, and a silenced device gets nothing either. Haptics are the documented pairing: `HapticFeedbackConstants.CONFIRM` is "a haptic effect to signal the confirmation or successful completion of a user interaction" and `REJECT` "the rejection or failure" [R35], reached through `View.performHapticFeedback` (which needs no `VIBRATE` permission) or Compose's `LocalHapticFeedback` [R34]
- **MUST** design the no-detection state as a designed state with a next action, not an indefinite viewfinder: a torch control where the device has one, the manual-entry path from §H, and an explanation. Usability research puts the user's patience at roughly 15 seconds and recommends offering a short URL or equivalent alternative where a scan cannot be relied on inside that window [R39] (S)
- **MUST** apply the wait-indication and message-surface rules from `spec/android/ui-components/` §A rather than inventing scanner-specific indicators, and the error-state wording rules from `spec/android/app-design-navigation/` §F
- **MUST** keep every on-screen scanner control (torch, cancel, manual entry, gallery) at a 48dp × 48dp minimum touch target [R36]
- **SHOULD** show a framing affordance that communicates where to aim and that scanning is live, and **MUST NOT** let that affordance imply a crop the detector does not actually apply — the detector sees the analysis frame, not the reticle
- **SHOULD NOT** auto-enable the torch: no vendor source defines a threshold for it, so an automatic trigger is an invented heuristic. The conformant construction is a visible, user-operated control (§C)

### F. Trust boundary — the decoded payload

- **MUST** treat every decoded payload as untrusted input, on the same footing as IPC and network input under `spec/android/security/` §D/§F. OWASP states the obligation for the adjacent channel directly: deep-link input "should be deemed untrustworthy and thus should always be validated" [R27], and a printed sticker is a lower bar for an attacker than a crafted link
- **MUST NOT** act on a payload without an explicit user action on a screen that shows the destination. The FTC's guidance to consumers is to "inspect the URL before you open it" [R30], which an app can only make possible by showing it; the risk is documented by the FBI for both tampered physical codes [R28] and codes in unsolicited mail [R29], and by NCSC UK, which notes that codes in email specifically "obscure malicious URLs" and "may bypass email security scanning tools" [R31]. No standards body states this as a numbered control, so this spec fixes it as a corpus rule (§Open Questions)
- **MUST NOT** auto-execute any payload class: no placing a call (`ACTION_CALL` dials directly and requires `CALL_PHONE`; `ACTION_DIAL` "shows a UI with the number being dialed, allowing the user to explicitly initiate the call" and is the only conformant choice) [R26], no sending an SMS, no joining a network, no submitting a form, no starting a payment
- **MUST** validate a scanned URL before it is offered as a destination: the scheme against an allowlist (`https` for web content; `javascript:`, `file:`, `content:`, and `intent:` rejected outright), the host by exact match where the app claims it, and the rendered form as the user will see it. IDN and punycode handling **MUST NOT** be assumed to be done for the app by the platform [R24]
- **MUST NOT** pass scanned text through `Intent.parseUri` or hand a scanned string to `startActivity` as an intent URI: this is the documented path by which an attacker reaches internal, non-exported components [R24]. It is a distinct vector from the intent redirection `spec/android/security/` §D forbids — that rule governs an intent arriving in extras, this one a string arriving through a camera — but it reaches the same class of harm and inherits the same prohibition
- **MUST** route own-domain destinations through verified App Links (`android:autoVerify` with `assetlinks.json`) rather than an unverified custom scheme, so the OS resolves the target instead of the app trusting a string [R25]. This is deliberately stricter than the SHOULD in `spec/android/app-design-navigation/` §E, which owns deep-link routing in general: there the origin is the platform, here it is whoever printed the code
- **MUST NOT** interpolate a scanned value into any interpreter — SQL, shell, HTML, a WebView `loadUrl`, or a URL path or query without encoding. `spec/android/security/` §F's parameterised-query rule and §D's WebView rules apply unchanged; the scanner is simply a new source of the same untrusted string
- **MUST** bound the payload before it is stored, rendered, or transmitted: a QR symbol carries up to 2,953 bytes in byte mode at version 40 [R40], which is enough to break a field that assumed an identifier. No vendor or standards source documents an oversized-payload denial-of-service class for scanners, so the bound is a defensive default rather than a cited mitigation (§Open Questions)
- **MUST NOT** join a network from a scanned `WIFI:` payload without an explicit user confirmation that shows the SSID: the `WIFI:` format is a de-facto ZXing convention rather than a standard [R48] (S) and carries the password in plaintext inside the code. Where the project controls the provisioning flow, it **SHOULD** use Wi-Fi Easy Connect (DPP), which is Android's own QR-based provisioning path and is cryptographically secured rather than password-bearing [R49]
- **MUST NOT** treat a URL shortener as an inspectable destination: the shortened form defeats the user's inspection step, so a shortened URL either resolves server-side under the app's control before being shown, or is presented as unverifiable

### G. Permissions and privacy

- **MUST NOT** declare or request the `CAMERA` permission at all on the code-scanner path — that is the path's defining property [R3], and requesting it anyway both contradicts `spec/android/security/` §E and forfeits the benefit that justified the choice
- **MUST**, on the in-app path, request the camera permission in context, at the moment the user asks to scan, with a rationale gated on `shouldShowRequestPermissionRationale` [R20][R21]; the UX rules are owned by `spec/android/app-design-navigation/` §F, which also carries the evidence that in-context requests are granted materially more often
- **MUST** degrade gracefully rather than dead-ending when the permission is denied or permanently denied: the manual-entry path from §H is the fallback, and a permanently denied state **MUST** be recognised and explained rather than re-requested into a dialog the system will no longer show [R20][R21]
- **MUST** keep the Play Data Safety declaration accurate to what actually happens to a payload, per `spec/android/security/` §E, which owns the general obligation: on-device decoding is one thing, transmitting the decoded value or the frame to a backend or a third-party SDK is another, and the declaration is the developer's responsibility with enforcement attached [R22]. No source found states an explicit exemption for on-device-only processing, so a skill **MUST NOT** assert one (§Open Questions)
- **SHOULD** note that the camera privacy indicator behaves differently across the two paths — camera access on the code-scanner path happens inside Play services rather than under the app's own permission grant [R3][R23]. This follows from the documented delegation model rather than from an explicit statement, and **MUST NOT** be presented to a user as a privacy guarantee

### H. Accessibility

- **MUST** provide a path to the same outcome that does not require aiming a camera — manual entry of the code's value, a link, or an equivalent action. This is the pattern's primary accessibility failure: a user who cannot see the code cannot locate, aim at, or frame it, and a scan-only flow has no keyboard-operable equivalent. Federal accessibility guidance states the print-side counterpart directly — provide a text alternative or link adjacent to the code [R37] (P)
- **MUST NOT** rely on WCAG SC 2.5.4 Motion Actuation for cover: the W3C's own Understanding document excludes camera aiming from its scope — the criterion "does not cover the movement necessary to point a device camera at a particular object such as a QR code" [R38]. The obligation the flow does carry is the alternative path above, not a motion toggle
- **MUST NOT** announce scan results through `announceForAccessibility` or `TYPE_ANNOUNCEMENT`: both are deprecated in Android 16 (API 36) because they "create inconsistent user experiences for users of TalkBack" [R32]. The conformant constructions are a live region (`Modifier.semantics { liveRegion = LiveRegionMode.Polite }`, or `setAccessibilityLiveRegion`) for the result, a pane title for the surface change, and `CONTENT_CHANGE_TYPE_ERROR`/`setError` for a failed scan [R32][R33]
- **MUST** announce a successful scan politely rather than assertively — assertive interrupts current speech and is reserved for time-critical content [R33] — and **MUST NOT** leave the transition from "scanning" to "scanned" perceivable only as a visual change
- **MUST** keep the decoded content reachable and readable by a screen reader on the confirmation surface from §F, since that surface is where the user is expected to make the trust decision

### I. Generating codes

- **MUST** set the encoder's character set explicitly (`EncodeHintType.CHARACTER_SET`) rather than inheriting the byte-mode default, which is ISO/IEC 8859-1 — a UTF-8 payload emitted without an ECI designator is read back as mojibake by a decoder that follows the default [R46] (S)
- **MUST** resolve the encoding conflict this creates instead of hiding it: **ML Kit does not recognise QR codes generated in ECI mode at all** [R2], so a code encoded with an explicit ECI header for correct UTF-8 is unreadable by the very scanner §A recommends building. A code intended for this corpus's own scanners therefore **MUST** restrict its payload to characters that survive the default interpretation, and any requirement for non-Latin payloads **MUST** be reported as the conflict it is rather than silently decided (§Open Questions)
- **MUST** render the quiet zone at the symbology's requirement — 4 modules for full-size QR (§B) — and **MUST NOT** assume the encoder does it: ZXing's `MARGIN` hint "specifies margin, in pixels, to use when generating the barcode" [R46], so a caller that leaves it at a default or sets it in the wrong unit produces a symbol whose margin is not 4 modules
- **MUST** choose the error-correction level deliberately (`EncodeHintType.ERROR_CORRECTION`) and record why, trading capacity against damage tolerance: the four levels recover roughly 7 %, 15 %, 25 %, and 30 % of codewords at L/M/Q/H, of which only the 15 % figure is stated by the symbology's originator, the others being consistently repeated but not traceable to primary text [R41] (S)
- **MUST** render each module at whole-pixel boundaries and **MUST NOT** produce a small bitmap and scale it up with interpolation — blurred module edges are a decode failure that looks like a rendering nicety. A vector or per-module draw at the display's density is the conformant construction [R56] (S)
- **MUST NOT** let a theme invert or tint the code: dark mode **MUST NOT** flip the polarity of a symbol the app expects to be scanned, and the code **MUST** keep a light quiet zone even where the surrounding surface is dark (§B) [R39] (S)
- **MUST NOT** place a logo or overlay over a finder pattern, and **MUST** treat any central overlay as an unstandardised practice: no standards body or the symbology's originator addresses overlay tolerance at all, so the only defensible construction is the highest error-correction level plus verification by actual scanning (§J), never a coverage percentage quoted as if it were normative
- **SHOULD** raise screen brightness while a code is displayed for another device to scan, through the window-level `WindowManager.LayoutParams.screenBrightness` override (`1.0` forces maximum, `-1.0` restores system control) [R50], and **MUST** restore it when the surface is left — there is no barcode-specific API for this
- **SHOULD** prefer a maintained encoder and record the choice: `com.google.zxing:core` is actively released, and the Compose-native alternatives are the vector-rendering path [R53][R56] (S)

### J. Verification

- **MUST** verify a scanning or generating surface against real codes rather than by inspection, and **MUST** include the adversarial cases as first-class fixtures: a damaged code, a low-contrast one, one at the edge of the §B pixel budget, one at an angle, and a payload that exercises §F's rejection paths (a `javascript:` URL, an over-long payload, a `WIFI:` payload)
- **MUST** exercise the permission-denied and permanently-denied paths as tests, not only the granted path — the graceful-degradation requirement in §G is otherwise unverified
- **SHOULD** use the emulator for the mechanical layer: an image can be imported into the emulator's virtual scene, and the documentation names this use explicitly — "This feature can be used to import custom images such as QR codes for use with any camera-based app" [R51]
- **MUST NOT** treat an emulator pass as evidence about focus, low light, distance, motion blur, or torch behaviour: the emulator documentation makes no claim about simulating them, and those are precisely the conditions §B and §C are about. Any claim of that class **MUST** come from a physical device, recorded with the device and the capture resolution it was made at
- **MUST** report the gap rather than invent a threshold: this repo has no general camera spec, and `spec/android/perceived-performance/` fixes startup and frame budgets rather than detection ones, so a skill needing a scan-latency budget, a frame-rate target beyond the documented 32 ms interval, or a detection-rate acceptance number **MUST** surface the gap and propose the spec extension (REQ-6, REQ-17)
- **SHOULD** keep device-bound scanning tests in the instrumented lane per `spec/android/test-automation/` §F rather than the per-commit suite

## Acceptance Criteria

The criteria below are a deliberate representative rollup of §A–§J, not a 1:1 mapping; every requirement bullet above is normative on its own. Two normative bullets are left to reviewer judgement rather than a mechanical criterion, because both are judgements about a skill's reasoning: the obligation to report the missing camera spec instead of inventing a detection budget (§J), and the refusal to promote unsourced sizing folklore into a requirement (§B).

- [ ] The access path is recorded with its reason; a bounded one-shot scan uses the Google code scanner, and any in-app scanner names the capability the code scanner could not serve
- [ ] No app on the code-scanner path declares or requests the `CAMERA` permission; every in-app path requests it in context with a rationale and degrades gracefully on denial and permanent denial
- [ ] The scanner-module and ML Kit model supply is an explicit decision, and the not-yet-downloaded state is a handled state rather than a silent failure
- [ ] `ImageAnalysis` carries an explicit `ResolutionSelector` sized against the 2-pixels-per-module budget; the VGA default is never accepted, and the deprecated target-resolution API is absent from new code
- [ ] Backpressure stays `STRATEGY_KEEP_ONLY_LATEST`, every `ImageProxy` is closed on every path, the wrapped `Media.Image` is never closed, and `rotationDegrees` reaches the `InputImage`
- [ ] Detection coordinates reach the overlay through `MlKitAnalyzer` or a `CoordinateTransformer`, never through hand-computed mapping
- [ ] Accepted formats are restricted to what the feature consumes; the app acts on `rawValue` (or `rawBytes`), never on `displayValue`; and a continuous scanner has both a stated acceptance rule rather than acting on the first decoded frame and a recorded duplicate-suppression rule so one physical code is not consumed repeatedly
- [ ] No required capability rests on a documented ML Kit exclusion (ECI-mode QR, FNC2/3/4, single-character 1D, sub-six-character ITF, Micro QR, rMQR, Structured Append, more than 10 codes per call, off-centre Data Matrix)
- [ ] Every decoded payload reaches an explicit user confirmation that shows the destination before anything acts on it; nothing auto-dials, auto-joins, auto-sends, or auto-submits
- [ ] Scanned URLs are scheme-allowlisted and host-checked, own-domain targets go through verified App Links, and no scanned string reaches `Intent.parseUri`, `startActivity` as an intent URI, a WebView, a query interpreter, or an unbounded field
- [ ] A non-camera path to the same outcome exists; scan results are announced through a polite live region rather than the deprecated announcement APIs; the decoded content on the confirmation surface is reachable and readable by a screen reader; and every scanner control meets the 48dp target
- [ ] Success is signalled through at least two channels and never through audio alone; the no-detection state offers a next action rather than an indefinite viewfinder
- [ ] Generated codes set the character set explicitly, keep a 4-module quiet zone, carry a recorded error-correction level, render at whole-pixel module boundaries, keep dark-on-light polarity under every theme, and leave the finder patterns uncovered
- [ ] Any generated code whose payload needs non-Latin characters carries the ECI-versus-ML-Kit conflict as a recorded decision rather than an unnoticed unreadable symbol
- [ ] Verification uses real codes including damaged, low-contrast, angled, and budget-edge fixtures plus the §F rejection payloads; no claim about focus, low light, distance, or torch rests on an emulator run

## Open Questions

All eight questions are parking-lot class: the requirements above state a working default or an explicit refusal to invent a number for each, so implementation proceeds without an answer.

- Duplicate-suppression interval for a continuous scanner: no vendor or research source states one, so this spec requires the value to be recorded at its definition site rather than fixing a number. Working default: per project.
- Non-Latin payloads in generated codes: ECI is the standard-conformant way to encode UTF-8, and ML Kit refuses ECI-mode QR outright [R2][R46]. There is no construction that satisfies both, so the choice is between an ECI code readable by other decoders and an ASCII-restricted payload readable by this corpus's own scanners. Working default: restrict the payload, record the restriction.
- Showing the decoded destination before acting: fixed as a corpus rule in §F on the strength of consumer-protection guidance [R30][R31] and shipped platform behaviour, but no standards body states it as a numbered control. Worth revisiting if OWASP MASVS adopts one.
- Data Safety and on-device processing: no source found states whether purely on-device decoding needs a declaration at all [R22]. Working default: declare what leaves the device, and treat the on-device case as unresolved rather than exempt.
- Oversized-payload denial of service: no vendor or standards-body source documents the class; only an academic preprint surfaced. §F's bound is therefore defensive rather than cited.
- Error-correction recovery percentages: only the 15 % figure at level M is stated by the symbology's originator [R41]; the 7 %/25 %/30 % figures are consistently repeated across secondary sources but were not traceable to primary text in this research pass.
- Missing owner for general camera work: photo capture, video, and gallery pipelines on CameraX are orphaned between this spec and `spec/android/uvc-microscope/`, which explicitly excludes built-in cameras. Working default: this spec owns only the scanning pipeline.
- Detection-rate acceptance number: the only quantified ML Kit comparison is vendor-published [R54] (S) and adversarial by construction, so no pass/fail detection rate is fixed here.
